# 2.1.0 · Ingestion spike

**Type:** spike — throwaway, no production code
**Deliverable:** an answer written into `PROJECT_PLAN.md` §5.12, and a deleted script
**Estimated:** ~30 minutes, a handful of Gemini calls
**Depends on:** nothing
**Blocks:** 2.1.5 (indexing), and possibly adds a new phase 2.1.5b (OCR pre-pass)

---

## Why this exists

Every later phase assumes Gemini File Search can read the PDFs we hand it. For
`uit.pdf` that is safe. For `iuh.pdf` it is unverified, and the two files are
structurally different in a way that matters — measured by parsing them, not by
looking at them:

| File | Pages | Text ops (`Tj`/`TJ`) | Font resources | Image XObjects |
| --- | --- | --- | --- | --- |
| `uit.pdf` | 25 | 3310 | 102 | 0 |
| `iuh.pdf` | 12 | 12 | **0** | 12 |

`iuh.pdf` declares **no fonts at all** and carries one full-page image per page.
There is no text in that file to extract. Anything Gemini returns from it must
come from OCR.

The Gemini API File Search documentation does not mention OCR. The OCR options
that surface in search — `useNativeText`, OCR parser config — belong to **Gemini
Enterprise / Vertex AI Search**, a different product. So this is genuinely
unknown, and it is not the kind of unknown to discover in Phase 3.

**The failure mode is why this goes first.** If File Search does not OCR, the
upload operation most likely still reports success. We would mark the document
`ready`, the list UI would look correct, and every IUH question would answer
"không có trong tài liệu hiện có" — which is *indistinguishable from our
refusal working correctly*. A silently empty index wearing the costume of good
behaviour is the worst outcome this product can have, because it is invisible.

Answering this now costs half an hour. Answering it in Phase 3 costs a rewrite
of the indexing path.

## What I will do

**1. Write `scripts/spike-index.mts`** — throwaway, in the same `.mts` style as
the existing scripts, run with `node --env-file-if-exists=.env.local`.

For each of `doc-to-test/uit.pdf` and `doc-to-test/iuh.pdf`:

- `uploadToFileSearchStore` with `displayName` set to the filename and `customMetadata: { spike: 'true' }` so the documents are identifiable and removable
- poll `ai.operations.get` until `done`, recording elapsed time and any `operation.error`
- run one `generateContent` with only the `fileSearch` tool, asking a question whose answer can only come from that document
- dump `candidates[0].groundingMetadata` in full

**2. Record, per file:**

| Question | Why it matters |
| --- | --- |
| Did the operation complete without error? | tells us whether failure is even detectable at upload time |
| **How long did indexing take?** | directly decides **D5** — if a 25-page PDF indexes in 8s, synchronous is fine; if it takes 90s, it is not |
| Is `groundingMetadata` present at all? | this is the field §5.7 layer 3 keys on |
| How many `groundingChunks`? | zero from a successful upload = the silent-empty-index case, confirmed |
| Does `retrievedContext.text` hold real Vietnamese text, or empty/garbage? | distinguishes "OCR worked" from "OCR produced noise" — noise is worse than nothing, because it grounds a wrong answer |
| Is `pageNumber` populated? | our citations promise a page; if it is absent for scans, the UI needs to handle a citation without one |
| Are Vietnamese diacritics intact? | OCR that drops diacritics changes meaning, and would quietly corrupt answers |

**3. Clean up.** Delete the two spike documents from the File Search store so
they cannot pollute later phases, and **delete the script**. Its output is a
decision, not code we keep.

**4. Write the answers into `PROJECT_PLAN.md` §5.12**, replacing the "open risk"
wording with what we actually measured.

## What the outcome changes

**If both files index with real text** — the happy path. 2.1.5 proceeds as
planned. The post-index check stays anyway, because it is cheap and it is the
only thing standing between a future bad upload and a silent lie.

**If `iuh.pdf` indexes nothing** — I bring you a plan for a new phase **2.1.5b ·
OCR pre-pass**: Gemini reads the scanned PDF with native vision
(`gemini-3-flash`, PDF as `inlineData`), we index the extracted text instead of
the original file, and `documents` gains a column recording that the text is
OCR-derived so citations can be honest about it. That is a real scope increase
and it gets its own plan and its own approval — I will not fold it into 2.1.5.

**If `iuh.pdf` indexes garbage** — worse than nothing, and the post-index check
becomes mandatory rather than defensive. We would also need a confidence
threshold, which I would bring you as its own decision.

### The methodology trap this spike walked into

The **first** run put both documents in the shared store and asked an unscoped
question. Every returned chunk was titled `uit.pdf` and none came from
`iuh.pdf` — which looks exactly like the silent-empty-index failure we came
here to find. It was not. Retrieval had simply ranked the text PDF higher.

Re-running with `metadataFilter: "docid=iuhpdf"` scoped retrieval to the one
document and showed it was fully indexed all along.

**Had we stopped at the first run we would have concluded the opposite of the
truth and built an OCR pre-pass we do not need.** In a shared store, "no chunks
from document X" is evidence about *ranking*, not about *indexing*, unless the
query is scoped. That distinction now matters twice: it is how the 2.1.5
post-index check has to be written, and it is a live hazard when interpreting
any Phase 3 refusal.

### Seven findings that change later phases

1. **`customMetadata` is `CustomMetadata[]`, not an object.** `[{ key, stringValue }]`. §5.3 said `{ documentId }` and was wrong. → **2.1.5**
2. **It round-trips.** `retrievedContext.customMetadata` returns the same array, so a citation resolves to a Supabase row exactly as §5.3 intends. Mechanism confirmed working, not assumed. → **2.2.2**
3. **`metadataFilter: "docid=<value>"` works.** Confirmed syntax. This is the post-index check's mechanism. → **2.1.5**
4. **No metadata signal reveals an empty index.** `sizeBytes` returned 865152 and 4163258 — the *raw uploaded file sizes*, not extracted text — and both documents read `state=STATE_ACTIVE`. So there is no cheap field to test. **The post-index check must be a real scoped retrieval query.** → **2.1.5**
5. **`documents.delete` needs `config: { force: true }`.** Without it: `400 FAILED_PRECONDITION — Cannot delete non-empty Document`. Every real document is non-empty, so the naive call fails 100% of the time. → **2.1.7**
6. **`mediaId` was `undefined` on every chunk.** §5.2 listed it as available. Do not build citations on it; `title` + `pageNumber` + `customMetadata` are what actually arrive. → **2.2.2**
7. **`gemini-3.7-flash` returned `503 UNAVAILABLE` persistently** — six attempts over ~75s, across two runs. `gemini-3.6-flash` answered first try. The model exists (confirmed via `models.list`); it is capacity-constrained. Our default model is the newest one, and it was unavailable for the entire time we tried. → **new decision D7**

### D5 is now answerable

Indexing took **10.0–14.6s** across four uploads of a 0.9 MB text PDF and a
4.1 MB scan. That is comfortably inside a serverless request budget, and it is
measured rather than guessed.

**Recommendation: D5 = Option A, synchronous with a ~60s timeout** — roughly 4×
the slowest observed run. Simple, one code path, no scheduler. 2.1.8's retry
covers the tail case, and the post-index check is identical under either option.

### New decision D7 — default model

`gemini-3.7-flash` being unavailable for ~75s straight is not something a
student asking about admissions deadlines should experience as a dead chatbot.
Options, for a later phase: pin `gemini-3.6-flash` · keep 3.7 with a fallback
to 3.6 on 503/429 · use `gemini-flash-latest`. Not urgent — 2.2.3 is where it
lands — but recorded now, while the evidence is fresh.
