# 9.6 — Connecting and disconnecting Google

## What had to change on the server first

`linkIdentity` is refused unless **Enable Manual Linking** is on. From the SDK's
own docblock:

> The **Enable Manual Linking** option must be enabled from your project's
> authentication settings.

So `enable_manual_linking = true`, pushed to hosted. The same push restored the
two settings a Phase 8 `config push` had overwritten with this file's
local-development values:

| Setting | Was on hosted | Now |
|---|---|---|
| `enable_manual_linking` | false | **true** |
| `email.enable_confirmations` | false (overwritten in Phase 8) | **true** |
| `mfa.totp.enroll_enabled` / `verify_enabled` | false (overwritten) | **true** |

`enable_confirmations` mattered most: hosted was accepting sign-ups from
addresses nobody had proved they owned. Sign-up already handled the no-session
response — it shows "check your email" — so no application code changed.

Verified on the container and against hosted:

```console
GOTRUE_SECURITY_MANUAL_LINKING_ENABLED=true
GOTRUE_MFA_TOTP_ENROLL_ENABLED=true
GOTRUE_MAILER_AUTOCONFIRM=false
$ curl -o /dev/null -w '%{http_code}' \
    https://…supabase.co/auth/v1/user/identities/authorize?provider=google
401          # the route exists; 401 because curl carries no session
```

## The push that failed, and what it forced

The first attempt was refused outright:

```
400 Email template modification is not available for free tier projects using
    the default email provider. Please upgrade your plan or configure a custom
    SMTP provider.
```

`config push` is **atomic**: the custom recovery template from 9.5 blocked
`enable_manual_linking`, the confirmation setting and everything else from
reaching hosted. Leaving it in place would have meant no auth setting could ever
be pushed again.

So the template is commented out in `config.toml`, and the file kept with a note
to uncomment it once custom SMTP exists. That is a real reversal of a 9.5
decision, and it needed a different fix — see below.

## Recovery had to move to a client page

With the default template, the recovery link returns the session in the URL
**fragment**, and a fragment never reaches the server. 9.5 solved that with
`{{ .TokenHash }}`; hosted will not accept the template, so that solution works
only locally — which is the worst possible split, since hosted is what real
users touch.

`/auth/recover` is a client page instead. It reads `window.location.hash`,
hands the tokens to `setSession`, clears the fragment from the address bar with
`history.replaceState`, and forwards to `/profile/password`. `resetPasswordForEmail`
now points there.

The parsing is a pure function with 8 tests, because it is the part with edge
cases: no fragment, a fragment with no tokens, one token but not the other
(`setSession` needs both), percent-encoded values, and the provider's own error
shape (`#error=access_denied&error_code=otp_expired`) which must be reported
rather than treated as "no tokens".

`safeNextPath` guards the destination even though it comes from our own email —
the value still arrives through a URL a person can edit.

## Disconnecting is refused when it would lock you out

GoTrue rejects unlinking the last identity, and an error after the click is a
poor way to learn that. `describeConnections` computes it up front:

```
identities        connected  canDisconnect  blockedReason
email + google    true       true           null
google only       true       false          lastIdentity
email only        false      false           null
```

When blocked, the button is visibly disabled and a tooltip explains what to do
first — *"Đây là cách đăng nhập duy nhất của bạn. Hãy đặt mật khẩu trước khi ngắt
kết nối Google."* — which is exactly what 9.4's "set a password" form is for. The
tooltip sits on a wrapper `span`, because a disabled control dispatches no
pointer events (the 6.5 finding).

The server checks again before unlinking. The UI decides what to *offer*; only
the server decides what is *allowed*, and the two are computed from the same
`auth.identities` list.

## Left for a browser

Linking redirects to Google and back, so the last step is yours: on `/profile`,
press Connect and confirm the row flips to "Đã kết nối" with Disconnect
available. The Google Cloud console already holds both callback URLs from Phase 8,
and linking reuses the same `/auth/callback` route.
