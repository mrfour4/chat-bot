# 8.4 — Signed in, but shown the login button

## What you reported

> now, i can logic with gg, but after login, my web show login button? why?

Google sign-in worked. The header still offered "Đăng nhập".

## Not a Google bug

`getSessionUser()` needs two things, and returns `null` if either is missing:

```ts
const { data: { user } } = await supabase.auth.getUser();
if (!user) return null;

const { data: profile } = await supabase.from("profiles")…
if (!profile) return null;
```

The session was fine. The **profile row was missing**, so the app could not
describe who you were, and every "are you signed in?" question answered no.

## Why the row was missing

| Fact | Value |
|---|---|
| `lqtu12369@gmail.com` created on hosted | 2026-08-30 **05:38** |
| `handle_new_user` created (init migration `20260830061744`) | 2026-08-30 **06:17** |
| Providers on that account | `email,google` |
| Profile rows | **0** |

The account is forty minutes **older than the trigger that creates profiles**.
It was made by email sign-up before the schema existed, so nothing ever gave it
a profile, and nothing since would have noticed.

**Password sign-in on that account had exactly the same bug.** Google only
brought it to light, because Google is what you happened to test with. Which
means the fix belongs to the data, not to the OAuth code.

## This answered the linking question

8.2 left automatic account linking open, because the official guide does not
cover it and it could not be tested without credentials. It is now settled:

```
email: lqtu12369@gmail.com   providers: email,google   (one user_id)
```

Supabase **linked** the Google identity to the pre-existing account on the
matching verified email rather than creating a second user. So a student who
signed up with a password and later uses Google keeps one account, one history,
one profile. No code needed for that; worth knowing it is the behaviour.

## The fix

`20260831091201_backfill_missing_profiles.sql` — one idempotent insert giving a
profile to every auth user without one, taking `full_name` from the same
`raw_user_meta_data` key the trigger reads. For the linked account that key was
filled by Google, so the backfilled name is the real one: `Tứ Lê Quí`.

A one-off `insert` typed into a SQL console would have fixed this database and
left the next one broken. As a migration it travels: applied locally, then
`supabase db push --linked`.

Verified:

```console
$ # local, then hosted
users without a profile: 0
$ # re-running the insert by hand
INSERT 0 0        # idempotent
$ npm run test:rls
29 passed, 0 failed
```

Hosted profiles afterwards:

| email | full_name | role |
|---|---|---|
| tu.le@devsamurai.com | Admin | teacher |
| lqtu12369@gmail.com | Tứ Lê Quí | student |

The new account is a `student`, which is the intended default — it can chat and
keep its own history, and cannot touch documents.

## Worth doing, not done here

A session with no profile currently produces a silent, confusing state: signed
in, told you are not. The trigger plus this backfill closes the only known
cause, but any future gap would look the same. Options, if you want one:

1. **Self-heal in `getSessionUser()`** — create the profile on demand when a
   session has none. Removes the failure mode entirely, at the cost of a write
   on a read path.
2. **Fail loudly** — log the user id when a session has no profile, so it shows
   up in the dev log rather than as a mysterious login button.

Neither is needed for correctness today, so neither was added without asking.
