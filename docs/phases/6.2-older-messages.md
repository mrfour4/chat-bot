# 6.2 — Older messages

## What you reported

> Currently the scroll position is not preserved correctly, causing the browser
> to continuously trigger `fetch more` until all messages have been loaded.

## The cause, from the scroller's own source

`MessageScrollerContent` reacts to its children changing in
`handleContentChange` (`@shadcn/react/dist/message-scroller`). Deminified, the
part that matters:

```js
const previousFirst = firstItemRef.current;
const index = previousFirst ? children.indexOf(previousFirst) : -1;
if (preserveScrollOnPrependRef.current && index > 0) { restorePrepend(); return; }
```

The restore runs only when the element that *used to be first* has moved down —
that is how the scroller recognises a prepend at all.

Our `OlderMessagesTrigger` was rendered as a `MessageScrollerItem` at the top of
the list, so it was the first child before the fetch and still the first child
after it. `index` was always `0`. The restore never ran, the viewport stayed
pinned at the top, the trigger was still on screen, and it fired again — as many
times as it took to exhaust the conversation.

No threshold to tune, and nothing wrong with `preserveScrollOnPrepend`. The
trigger was standing in the doorway it was watching.

## The change

The trigger leaves the message flow. It becomes a sibling of the viewport,
positioned over the top edge like `MessageScrollerButton` already is, and reads
`useMessageScrollerScrollable().start` from the same context. The first child of
the content is now a real message, so a prepend moves it down, `index > 0`, and
the scroller restores the position itself.

## Where the viewport lands

You asked for msg 25 — the newest of the newly loaded batch, the one adjacent to
where you were. The scroller's own restore keeps the *previous* first message
under the pointer, which leaves msg 25 just above the fold. So after the prepend
we scroll explicitly to the last message of the page we just received:

```ts
scrollToMessage(page.messages.at(-1).id, { align: "start" })
```

That is one message further up than the library's restore, it matches the example
you gave, and it settles `start` to `true`, which is what actually breaks the
loop: the trigger can only fire again once you scroll back up.

## Verify

- Open a seeded conversation, scroll to the top: one fetch, not many.
- After it lands, the message at the top of the viewport is the newest of the
  batch just loaded, with the message you were reading below it.
- Keep scrolling up: one fetch per arrival at the top, until "no older messages".
