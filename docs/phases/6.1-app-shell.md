# 6.1 — App shell height, page width

## What you reported

> When the number of messages increases, the chat input bar is pushed outside the
> viewport.

> On desktop the History UI appears unnecessarily small. The current `max-width`
> is too restrictive.

## Why the composer left the screen

`body` was `min-h-dvh`. That is a *minimum*: the body grows with its content, so
`main` had no definite height, so `flex-1 min-h-0` on the scroller had nothing to
be a fraction of. The scroller sized itself to the messages, the column grew past
the viewport, and the composer — correctly placed after it — went with it.

`min-h-dvh` is right for a document. It is wrong for an app shell, which is what
the chat is: a fixed frame with one scrolling region inside it.

## The change

`body` becomes `h-dvh overflow-hidden` and `main` becomes `min-h-0 flex-1
overflow-y-auto`. Now every page gets a definite height:

- Chat pages fill it and scroll internally, so the composer is pinned.
- History, Documents and Login are longer than the frame and scroll in `main`.

One scrollbar either way — `main` cannot overflow on a chat page, because the
column shrinks the scroller to fit.

## Width

`max-w-3xl` on History was chosen when the page was a list of six sentences. It
now carries a toolbar, a virtualized list and per-row menus. History and the
header go to `max-w-5xl`, Documents to `max-w-6xl` — the table has four columns
and a name that can be a hundred characters (6.8).

Chat keeps `max-w-2xl`. Line length is a reading decision, not a layout one, and
prose past ~75 characters is harder to read, not easier.

## Verify

- Ask enough questions to overflow, on `/` and on `/chat/[id]` — the composer stays put.
- History, Documents and Login still scroll to the bottom.
- The header stays fixed; no page scrolls sideways.
