# 5.3 — Document lifecycle: rename, archive, delete

**Goal.** The model behind the table 5.4 renders: six statuses, attribution,
and the three actions.

---

## 1. Six statuses, and why they are not an enum

| Display | Stored as | Means |
| --- | --- | --- |
| Uploading | `status = 'pending'` | the file is stored, indexing has not started |
| Indexing | `status = 'indexing'` | a worker holds it |
| **Ready** | `status = 'ready'` | the assistant can answer from it |
| **Failed** | `status = 'failed'` | it never indexed; `error_message` says why |
| Archived | `archived_at is not null` | out of Gemini, PDF kept |
| Deleted | `deleted_at is not null` | out of Gemini and Storage; a tombstone row |

Your four had no Ready and no Failed. Those are the two a teacher most needs to
tell apart, and §5.12 is the whole reason: a document that failed to index and
one that is answering questions look identical from a list that will not say.

**Archived and deleted are timestamps, not `document_status` values.** `status`
is the indexing state machine. An archived document has to remember that it
once indexed cleanly, or un-archiving would be a guess about what to restore it
to. Keeping them apart makes un-archive one column and `displayStatus()` a
six-line function with a test for each branch.

## 2. Archive removes it from Gemini

File Search has no "disable", so leaving retrieval scope means
`documents.delete`. Archiving therefore nulls `gemini_document_name`, and
un-archiving sets `status` back to `pending` and re-runs the indexing job — the
PDF is still in Storage, which is exactly what 3.3 bought.

Un-archive costs one index. Worth it: the alternative is a `metadataFilter`
that has to enumerate every archived document, grows without bound, and fails
by silently including something rather than by erroring.

## 3. Delete keeps the row

The file goes from Storage and from Gemini, as you specified. The row stays,
badged Deleted, hidden behind the status filter — otherwise "Deleted" could
never be a status anyone sees.

The unique checksum index becomes **partial** (`where deleted_at is null`).
Without that, deleting a document would permanently forbid uploading that file
again — the tombstone would hold its checksum forever.

## 4. Renaming, and the citation problem

`ai.fileSearchStores.documents` has `list`, `get` and `delete`. **There is no
update.** `displayName` is written once, at upload. So the mapping option is
the only one that exists — and it is the better one anyway, because the mapping
already exists: upload stamps `docid` into `customMetadata` (§5.3), and
`extractCitations` reads it back.

`resolveCitationTitles()` replaces the Gemini-supplied `fileName` with the
row's current `title`, and it runs **at render, not at persist**: a rename has
to reach messages written last week, not just the next one. Both readers go
through it — `/api/chat` on the way out, and `/chat/[id]` when loading a saved
conversation.

It reads through the admin client, narrowed to `id, title`. It has to: only
teachers may read `documents`, and the people looking at citations are students
and guests. Same shape as the public document list in §5.4.

## 5. Authorization, which the soft delete quietly broke

The old rule was "any teacher reads all; deletes only their own", carried by a
`DELETE` policy. **A soft delete is an `UPDATE`** — so that policy stopped
covering the action it existed for, without failing.

The replacement, and a widening you did not ask for but the table implies:

- **Any teacher may rename or archive any document.** The library is shared,
  and this is the only reason an "Updated by" column can ever differ from
  "Uploaded by".
- **Only the uploader may delete**, matching the old rule. `WITH CHECK` refuses
  a `deleted_at` set by anyone else, and `USING` refuses any further edit to an
  already-deleted row by anyone else.
- **`updated_by` must be the caller.** Otherwise attribution is a field anyone
  can forge and the column is decoration.
- **`uploaded_by` and `checksum` are immutable**, enforced by a trigger.
  `WITH CHECK` sees only the new row, so it *cannot* express this — and without
  it a teacher could take ownership of a colleague's document and then delete
  it, passing every policy on the way. This is the hole the check was hiding.

**Teachers can now read the profile directory.** `profiles_select_own` was the
only `SELECT` policy, so both attribution columns would have rendered blank for
every row a teacher had not touched — a working join that looks like missing
data. Merged into one policy rather than added beside it, because two
permissive policies both run on every row; the advisor flagged it and
`is_teacher()` would have made it real.

## 6. Verification

`npm run test:rls` — 17 → **25 checks**. The six new ones were then falsified
by dropping the trigger and replacing the update policy with a permissive one:
three failed, naming exactly what leaked (`ownership was reassigned`,
`deleted_at was set`, `updated_by was forged`). A check that cannot fail is not
a check.

Seed gains a second teacher. Half these rules are unobservable with one.
