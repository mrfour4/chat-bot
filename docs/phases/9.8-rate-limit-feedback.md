# 9.8 — Say when you refuse

## What you reported

> When I click "Send reset link", I don't receive any password reset email.

And, on rate limits generally:

> Please do not silently ignore or block the action without feedback, as users
> may think it is a bug.

## Why no email arrived

Our action deliberately discarded the result, so nobody — user or developer —
could see what happened. Asking hosted directly:

```console
error: {"status":429,"code":"over_email_send_rate_limit","message":"email rate limit exceeded"}
```

From Supabase's own rate-limit documentation:

> **2 emails per hour** with the built-in email provider. You can only change
> this with a custom SMTP setup.

Two per hour, project-wide, for every kind of auth email together. A couple of
test attempts exhausts it.

**Not something a push broke.** `email_sent = 2` in `config.toml` matches the
platform's cap for the built-in provider, and it never appeared as a change in
either push diff, so hosted always had it. What 9.6 *did* do is make that budget
scarcer: turning `enable_confirmations` back on means sign-up confirmations now
compete for the same two.

## The real bug was the lie

The action always answered *"Nếu địa chỉ này có tài khoản, chúng tôi đã gửi liên
kết đặt lại mật khẩu."* — even when Supabase had refused to send anything. The
neutral wording exists so the page cannot be used to discover which addresses are
registered, and that reasoning is sound. Applying it to *every* outcome was not:
a refusal is not a fact about the account.

It is also safe to report, and this is the key point: `resetPasswordForEmail`
returns success for an unknown address by design, precisely to prevent
enumeration. So an error is never an existence signal — it is always a genuine
failure, and can be shown in full without leaking anything.

Now: a 429 says so plainly, any other error says the email could not be sent,
and only a real success claims one was. The forgot-password form already showed
both an inline destructive alert and a toast, so the message cannot be missed.

## The same fault, worse, in sign-in

Following the feedback beyond the reported case found this:

```ts
signInError = error.status ? t("invalidCredentials") : t("configError");
```

**Any** error with a status became "Email hoặc mật khẩu không đúng." Sign-in has
its own limit — `sign_in_sign_ups = 30` per five minutes — so a rate-limited user
was told their password was wrong. They would then retype it, fail again, and
reasonably conclude the account was broken. Sign-up had the same shape.

`authErrorKind` now classifies once, and all three actions share it:

| Kind | When | Message |
|---|---|---|
| `rate-limited` | 429 | "Bạn đã thử quá nhiều lần. Vui lòng đợi vài phút rồi thử lại." |
| `refused` | any other status | the specific reason (wrong credentials, etc.) |
| `unreachable` | no status at all | the Supabase configuration message |

Four tests, falsified by removing the 429 branch: 1 of 4 fails.

## What to do about the two-per-hour limit

For real use, **custom SMTP** is the answer — it lifts the limit and, as a
bonus, unblocks the Vietnamese recovery template 9.6 had to comment out, since
free-tier projects on the built-in provider cannot modify templates at all.
Resend's free tier is 3,000/month.

For development, the local stack has no limit and Mailpit catches everything at
<http://127.0.0.1:54424>.

## The clipped menu

The screenshot showed "Theo hệ thống" cut off at the menu's edge — worse than
the wrapping it replaced. My 9.7 fix added `whitespace-nowrap` to the item
without asking why the menu was too narrow.

The popup is `w-(--anchor-width)`: its width is pinned to the **trigger**, which
here is a 28px icon button, floored at `min-w-32` (128px), with
`overflow-x-hidden`. So the text had 128px minus `pr-8` for the checkmark, and
`nowrap` turned a wrap into a clip.

`className="w-auto"` lets the menu size to its content. Applied to all four
menus that hang off an icon button — theme, language, document actions and
conversation actions — because every one of them had the same latent flaw and
only the longest label had exposed it.
