# 2.3.1 · Chat route

**Type:** route · **API calls: a handful for verification**
**Depends on:** 2.2.3 · **Blocks:** 2.3.2

`POST /api/chat` → `{ answer, citations, grounded, reason }`, complete and
already guarded (§5.15 — no streaming).

## Rate limiting is not optional here

This endpoint is reachable **without an account**, and every call spends real
Gemini quota. On the free tier the entire day's 20 requests could be drained by
one script in about a second — by a bored visitor, or by a client-side retry
loop we wrote ourselves.

So: 8 requests per minute per caller, fixed window, keyed on
`x-forwarded-for` / `x-real-ip`.

**It is in-memory, and the comment says so.** The counter lives in one server
instance, so it does not hold across a horizontally scaled deployment. It stops
casual abuse and accidental loops, which is the real threat for an MVP. Redis
or platform rate limiting is the production answer, and this is the seam it
drops into. Writing that down beats leaving a future reader to discover the
limitation from an incident.

## Other decisions

**History is capped at 6 turns.** Enough for a follow-up to resolve
*"còn chỉ tiêu thì sao?"*, without a long conversation quietly growing every
request — and cost — without limit.

**Questions cap at 1000 characters**, and the body is parsed with `zod`, so a
malformed request fails at the edge rather than inside the model call.

**A quota failure returns HTTP 200** with `grounded: false, reason: "error"` and
the Vietnamese message. The request succeeded; the *answer* did not. The client
renders one thing — a message — rather than branching on transport status.

**Rate limiting runs before validation.** A flood of malformed requests is still
a flood.
