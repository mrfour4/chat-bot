# 4.1 — Prettier, four spaces

**Goal.** One formatter, four-space indentation, applied to the whole
repository — before anything else, so later diffs show changes rather than
reformatting noise.

---

## Why this is its own commit

A reformat touches nearly every line of every file. Mixed with real work it
would make review impossible: the interesting three lines would sit inside a
2,000-line diff. Landed alone, `git log --follow` and `git blame -w` both stay
usable, and every later phase reads as what it actually did.

## The setup

Prettier as a dev dependency, pinned. `.prettierrc.json`:

```json
{ "tabWidth": 4, "semi": true, "singleQuote": false, "trailingComma": "all" }
```

Four spaces as asked. The rest matches what the codebase already does, so this
phase changes indentation and nothing else about how the code reads.

**`.prettierignore`** covers `.next`, `node_modules`, generated files
(`src/lib/database.types.ts` is regenerated by the Supabase CLI and would drift
back on every `npm run db:types`), and `supabase/migrations` — SQL that has
already been applied to a hosted database is not worth reformatting.

**`package-lock.json` is excluded** — npm owns that file. It is reformatted
anyway, but by npm rather than by us: npm detects the indentation of
`package.json` and mirrors it into the lockfile, so making `package.json`
four-space made the lockfile four-space on the next `npm install`. That is
stable, not churn, and it is npm's decision rather than Prettier's.

**Markdown is excluded.** Prettier rewraps prose, which would rewrite every doc
in `docs/` for no benefit and lose the line breaks that keep them readable in a
diff.

## Scripts

- `npm run format` — write
- `npm run format:check` — verify, for CI

## Verification

`npm run format:check` clean, then the full suite: `npm test`,
`npm run typecheck`, `npm run lint`, `npm run build`. A formatter that changes
behaviour is a formatter with a bug, and this is how we would know.
