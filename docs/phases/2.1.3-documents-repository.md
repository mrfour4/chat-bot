## An honest scope note

Most of this phase is thin wrappers over PostgREST calls. **I am not going to
write mock-heavy tests for those.** Asserting that `markReady` called
`.from("documents").update(...)` tests the mock, not the code: it would pass
with the wrong column name, the wrong table, or RLS denying every write. Such a
test costs real maintenance and buys false confidence.

The plumbing gets verified for real when 2.1.6 lists documents in the browser
and when 2.1.5 writes a status back — against an actual database, where a wrong
column name fails loudly.

What *does* get tested here is the two pieces with real logic:

1. **`sha256Hex`** — checked against published vectors, so dedupe rests on something verified rather than on it "looking right"
2. **`describeError`** — turns an unknown thrown value into a short Vietnamese message fit for a database column and a teacher's screen

This is the same standard as 2.1.2, applied honestly: test the decisions, not
the wiring.

## The design decision: the client is injected

Every function takes its Supabase client as an argument rather than importing
one:

```ts
export async function listDocuments(supabase: DocumentsClient): Promise<DocumentRow[]>
```

Three reasons, in order of importance:

1. **RLS stays meaningful.** A teacher listing documents must go through the *user's* client so policies apply. A background write-back after indexing has no session and must use the secret-key client. If the repo picked its own client it would have to pick one of those and be wrong half the time — most likely by reaching for the secret key everywhere, which quietly turns §5.4 off.
2. **No `server-only` import**, so these modules are testable at all. This is the trap flagged in 2.1.1, and avoiding the import beats stubbing it.
3. The caller can see, at the call site, which authority a write is happening under.

## Interface

```ts
// src/lib/documents/repo.ts
type DocumentsClient = SupabaseClient<Database>;

listDocuments(supabase): Promise<DocumentRow[]>              // newest first
findByChecksum(supabase, checksum): Promise<DocumentRow | null>
createDocument(supabase, input: {
  title: string; fileName: string; fileSize: number;
  checksum: string; uploadedBy: string;
}): Promise<DocumentRow>                                     // status: pending
markIndexing(supabase, id): Promise<void>
markReady(supabase, id, geminiDocumentName): Promise<void>
markFailed(supabase, id, message): Promise<void>
deleteDocument(supabase, id): Promise<void>
getDocument(supabase, id): Promise<DocumentRow | null>
```

```ts
// src/lib/documents/checksum.ts
export async function sha256Hex(bytes: Uint8Array): Promise<string>;
```

```ts
// src/lib/documents/errors.ts
export const MAX_ERROR_MESSAGE = 500;
export function describeError(error: unknown): string;
```

**`sha256Hex` uses Web Crypto (`crypto.subtle.digest`)**, not `node:crypto`, so
the same function works whichever runtime a route ends up on. Node 24 exposes
`crypto` globally, so there is no import and nothing to configure.

**`describeError` truncates at 500 characters.** Gemini errors arrive as long
JSON blobs; the whole thing in `documents.error_message` makes the table
unpleasant to read and the failure card unreadable. It also handles non-`Error`
throws, which is the case that would otherwise land `"[object Object]"` in front
of a teacher.

## Tests

`checksum.test.ts` — 3 tests:
- empty input → `e3b0c442...b855` (the published SHA-256 of the empty string)
- `"abc"` → `ba7816bf...ad15` (the FIPS 180-2 vector)
- two different inputs produce different digests

Using published vectors rather than a snapshot means the test would catch a
wrong algorithm or wrong encoding, which a snapshot of our own output cannot.

`errors.test.ts` — 4 tests:
- an `Error` yields its message
- a string throw yields the string
- an object with no message yields a Vietnamese fallback, not `[object Object]`
- an over-long message is truncated to `MAX_ERROR_MESSAGE` with an ellipsis

**Worth noting about that:** `npm run typecheck` is not a weak substitute here.
`database.types.ts` is generated from the actual schema, so a wrong column or
table name in `repo.ts` fails typecheck. The thing a mock test would have
checked is checked already, by the compiler, against the real database shape —
which is why writing those tests would have added maintenance without adding
coverage.

`update()` sets `updated_at` explicitly on every status change, so the column
means what it says without depending on a trigger we did not write.
