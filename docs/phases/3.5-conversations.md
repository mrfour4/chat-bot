# 3.5 — Conversations and history navigation

**Goal.** Clicking a history item opens that conversation with its messages, in
order.

---

## The data model was already right

`conversations` (id, user_id, title, created_at) and `messages`
(conversation_id, role, content, citations, created_at) have existed since the
initial migration, with `messages_conversation_id_idx` ordering by
`created_at`. `/api/chat` already accepted a `conversationId` and already
returned the one it used.

So this phase is **navigation, not schema**. No migration.

The convention, stated plainly because you asked for one:

- a conversation is a list of messages and has an id
- a message belongs to exactly one conversation and carries its role
- `/chat/<conversation-id>` is the conversation
- `/history` lists conversations; `/` starts a new one

## What changed

**The history page was rendering a transcript, not a list.** It loaded *every
message of every conversation* — one query per conversation — then displayed a
title and a date. Now one query returns conversations with their message counts
as a PostgREST embedded aggregate.

**`/chat/[id]`** loads the conversation through the user's client, so RLS
decides. Someone else's conversation is *absent*, and the page answers 404
rather than 403 — 403 would confirm it exists.

**`AskBox` takes `initialMessages`.** Stored rows map onto exactly the shape it
already held in state, so a resumed conversation and a live one are the same
thing from the first render onwards. Persisted answers are marked grounded
because the §5.7 guard is what allowed them to be stored at all.

**The URL updates when a conversation is born.** Ask a first question on `/`
and the address bar becomes `/chat/<id>` via `window.history.replaceState` —
confirmed supported and router-integrated in this version of Next
(`docs/01-app/01-getting-started/04-linking-and-navigating.md`). It costs no
navigation, no refetch and no remount of a list we are already holding.
`replace`, not `push`: the empty page you started from is not somewhere to go
back to.

Before this, a signed-in student who asked a question and refreshed lost the
thread from view. It was saved the whole time — which is worse, not better,
because the app looked like it had forgotten.

## Verification

Eight checks against the hosted database, no Gemini:

```
PASS  create conversation
PASS  append messages
PASS  summary query returns embedded count      (the shape the list depends on)
PASS  messages come back in order
PASS  citations survive the round trip
PASS  a signed-out client sees nothing
PASS  cleanup removed it
PASS  messages cascade-deleted with the conversation
```

**One failure, and it was mine.** The first run failed with *null value in
column "citations" violates not-null constraint*. A bulk insert whose objects
have different keys makes PostgREST send `NULL` for the keys it did not see —
my fixture omitted `citations` on the user rows. `appendMessage()` always sets
it, so no app code was affected, but it is worth knowing before anyone writes a
batch insert here.

Yours in the browser: ask, refresh, confirm the URL carried the conversation;
open `/history`, click a row, confirm the messages are all there in order.
