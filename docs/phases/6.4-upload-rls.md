# 6.4 — Upload RLS

## What you reported

```text
{ code: '42501', message: 'new row violates row-level security policy for table "documents"' }
```

## What it actually was

Not the mock server, and not authentication. The upload route was refused by our
own policy.

`documents_update_teacher` (from 5.3) carries this in its `WITH CHECK`:

```sql
and updated_by = (select auth.uid())
```

The upload route runs on the *user's* client, and right after the insert it calls
`setStoragePath` to record where the PDF landed. That update never set
`updated_by`, so the new row had `null` there, `null = uid` is `null`, the check
failed, and Postgres reported it with the message above — which names "new row"
for updates as well as inserts, which is what made it look like the insert.

Verified against the local database rather than reasoned about, all in one
rolled-back transaction as the seeded teacher:

```text
INSERT=ok
UPDATE_no_updated_by  = 42501 new row violates row-level security policy
UPDATE_with_updated_by = ok
```

**This has been broken since 5.3 and no test caught it.** The RLS suite checks
the policy, and the policy is right. Nothing checked the route that has to
satisfy it, and the Gemini quota ran out before anyone uploaded again.

`resetToPending` on the Retry route had the same hole, for the same reason.

## The fix, and why it is a trigger

Passing an actor id into `setStoragePath`, `resetToPending` and `markFailed`
would work, and would leave the next route that writes to this table free to
forget again. The column means "the last person who touched this row", and the
database knows who that is:

```sql
create function public.documents_stamp_updated_by()
returns trigger ... as $$
begin
  if auth.uid() is not null and new.updated_by is not distinct from old.updated_by then
    new.updated_by := auth.uid();
  end if;
  return new;
end;
$$;
```

Three properties make this the right shape:

- **It cannot be forgotten.** Any update through any route is stamped.
- **It does not overwrite an explicit value.** Rename, archive and delete already
  set `updated_by` themselves; the trigger only fills a value that did not change.
- **The indexer is not a person.** Background jobs run as service role, where
  `auth.uid()` is null, so the trigger leaves the column alone. A file finishing
  its indexing does not rewrite who last edited it.

`WITH CHECK` is evaluated after `BEFORE` triggers, so the stamped row satisfies
the policy. Confirmed on the local database, including a second teacher editing
a document uploaded by the first: `updated_by` became the second teacher.

## Re-uploading

You also asked that deleted files be uploadable again while active ones are not.
Both already hold, and now have tests: the unique checksum index is partial
(`where deleted_at is null`), and `findByChecksum` ignores deleted rows, so a
tombstone blocks nothing. An active or archived row still refuses with a message
naming the document.

## Verify

- `npm run test:rls` — 28 checks, including three new ones. Dropping the
  trigger fails exactly the two that describe the upload path, with the 42501
  you reported.
- `npx vitest run --config vitest.api.config.mts src/lib/documents/reupload.itest.ts`
- Upload a PDF with the mock running: it reaches `indexing`, not 42501.
- Delete it, upload the same file again: accepted.
- Upload the same file twice while it is live: refused, by name.
