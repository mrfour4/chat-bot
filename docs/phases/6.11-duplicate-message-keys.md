# 6.11 — Duplicate message keys

## What you reported

> Encountered two children with the same key `b7773ace-…`. Keys should be unique…

The older messages arrived and rendered correctly. They arrived twice.

## Not the query

`listMessagesPage` uses a strict keyset — `created_at < X or (created_at = X and
id < Y)` — so one request can never overlap what is already loaded, and
`paging.itest.ts` already walks a 60-message conversation asserting no message is
returned twice, including ties on `created_at`. Two identical pages meant two
identical *requests*.

## The cause: an initial snapshot that says "at the top"

The scroller's state store is created with

```js
ge = { start: false, end: false }
```

and corrected in a `useLayoutEffect` that applies `defaultScrollPosition`. My
trigger from 6.2 reads that store through `useSyncExternalStore`, so its mount
effect sees the value from *render* — the uncorrected `start: false` — and
concludes the viewport is at the top before it has been positioned at the end.

So it fetched on mount. And because Next 16 enables React Strict Mode by default,
that mount effect runs twice, both invocations before `older.isPending` has
committed. The `olderPending` guard is React state and cannot gate two calls in
one commit: two requests went out with the same cursor, and the same 25 messages
were prepended twice.

This was mine, introduced in 6.2 when the trigger moved out of the message flow.

## Three changes, at three levels

**Do not act on a snapshot the scroller has not taken yet.** The trigger arms
itself one animation frame after mount, by which time the layout effect has run
and `start` is true for a viewport anchored at the end. Arming is state rather
than a ref, so the check re-runs — a conversation too short to scroll still loads
its older messages instead of waiting for a scroll that can never happen.

**Make the guard synchronous.** `loadOlder` records the cursor it is requesting
in a ref before calling `mutate`, and refuses to request the same cursor twice.
A ref updates immediately, so a doubled effect is refused on its second call
rather than a render later. Cleared in `onSettled`, so a failed page can be
retried.

**Make the state incapable of holding a duplicate.** `prependMessages` drops any
incoming message whose id is already present, and any repeat within the incoming
page. This is not a mask over the two fixes above: it is the invariant those
fixes exist to protect, and now nothing upstream — a retry, a double effect, a
future caller — can put two messages with one id into the list.

## Verify

- `npm test` — five tests on the merge; removing the dedupe fails four.
- Open a long conversation: no request for older messages until you scroll.
- Scroll to the top: one request, one page, no React key warning.
