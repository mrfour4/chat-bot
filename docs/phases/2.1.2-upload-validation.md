## Why this exists, and why it is test-first

This is the only thing standing between the File Search store and whatever a
browser hands us. It is pure — no network, no database, no clock — so it is
cheap to test exhaustively and expensive to get wrong. Exactly the shape that
earns tests before implementation.

Splitting it out from the route also means 2.1.4 can be about auth, dedupe and
persistence, without validation logic tangled through it.

---

## The design decision that matters: MIME is a hint, bytes are the truth

`File.type` comes from the browser, which infers it from the file extension.
Renaming `payload.exe` to `payload.pdf` produces a `File` reporting
`application/pdf`. So a MIME check alone is not a check.

**Both, in order:** MIME as a cheap early reject for honest mistakes, then the
`%PDF-` magic bytes as the actual gate. A file passes only if its first five
bytes are `0x25 0x50 0x44 0x46 0x2D`.

This also means the caller must read the bytes before validating. That is not
extra work — 2.1.4 needs the bytes anyway for the sha256 duplicate check.

## Interface

```ts
// src/lib/documents/validate.ts

export const MAX_UPLOAD_BYTES = 20 * 1024 * 1024; // 20 MB

export type UploadRejectionCode =
  | "empty"
  | "too-large"
  | "wrong-mime"
  | "not-a-pdf";

export type UploadValidation =
  | { ok: true }
  | { ok: false; code: UploadRejectionCode; message: string };

export function validateUpload(input: {
  fileName: string;
  mimeType: string;
  bytes: Uint8Array;
}): UploadValidation;
```

`code` is for us (tests, logs, HTTP mapping); `message` is Vietnamese and goes
straight to the teacher. Returning both keeps the UI free of a translation
table and keeps tests asserting on something stable.

**Why 20 MB:** Gemini's own limit is 100 MB, and our largest real sample
(`iuh.pdf`, a 12-page scan) is 4.1 MB. 20 MB leaves generous headroom for a
longer scanned prospectus while still rejecting anything that is obviously not
an admissions document. It is one constant, easy to raise.

**Order of checks:** empty → too large → wrong MIME → not a PDF. Cheapest and
most certain first, and it means a 30 MB file is rejected on its size rather
than after inspecting content.

## Tests, written first

`src/lib/documents/validate.test.ts`:

1. accepts a minimal valid PDF (`%PDF-1.7` + bytes)
2. rejects an empty file → `empty`
3. rejects over the cap → `too-large` (constructed at `MAX_UPLOAD_BYTES + 1`, not a literal, so the test follows the constant)
4. accepts exactly at the cap — the boundary, because off-by-one here silently rejects a legitimate document
5. rejects `image/png` → `wrong-mime`
6. **rejects a file claiming `application/pdf` whose bytes are not a PDF → `not-a-pdf`** — the renamed-executable case, and the reason magic bytes exist
7. rejects a PDF whose header appears after a leading byte — we require the signature at offset 0
8. every rejection message is non-empty and Vietnamese (asserted via diacritics, so an English fallback cannot slip through)

Test 6 is the one that justifies the whole design; the others are guard rails.
