# 5.4 — The documents table

**Goal.** Documents as a table: name, uploaded by, updated by, status, actions.
Search by name, filter by status, page through the rest.

---

## 1. TanStack Table v9, and the skill that exists

`@tanstack/react-table@9.2.4` ships **six agent skills** — the first TanStack
package in this project that does. Loaded before writing any of this:
`getting-started`, `table-state`, `with-tanstack-query`.

They are worth having, because v9 is not v8 and this codebase's training-data
instinct is v8:

| v8 | v9 |
| --- | --- |
| `useReactTable({ getCoreRowModel: getCoreRowModel() })` | `useTable({ features, columns, data })` |
| every feature always present | `tableFeatures({ rowPaginationFeature })` — state that is not registered **does not exist** |
| `flexRender(cell.column.columnDef.cell, cell.getContext())` | `<table.FlexRender cell={cell} />` |

shadcn's own data-table examples are still v8, so they are reference for
markup only.

**No features are registered at all** — `tableFeatures({})`. That is the
conclusion the skills push you to rather than away from: registering
`rowPaginationFeature` with `manualPagination: true` would add a state slice, a
`rowCount` option and a second owner for something the query already owns, in
exchange for nothing, because the server has already sliced the page. Table
renders rows and headers; Query holds page, search and filter. The
`manualPagination` trap the skill warns about — it switches off client slicing
but does not fetch — cannot be fallen into if the feature is never registered.

The one mistake that did apply: a fresh `data: rows ?? []` fallback on every
render invalidates every data-dependent model. `EMPTY_ROWS` is module scope.

## 2. Paging is server-side, and page-based as you asked

`GET /api/documents?q=&status=&page=&pageSize=` → `{ documents, total, page,
pageSize }`. Every server-owned slice is in the query key, or Query serves
page 1's cache for page 2. `placeholderData: keepPreviousData`, so paging does
not blink through an empty table.

**Search escapes `%` and `_`.** They are wildcards in `ilike`, so a teacher
searching for a literal `100%` would otherwise match everything. It searches
`title` and not `file_name`: PostgREST's `or` takes a comma-separated string,
so a comma in the search term would silently rewrite the filter.

**The status filter translates.** Display statuses are not stored (5.3), so
`archived` becomes `archived_at is not null and deleted_at is null`, and so on.
The default excludes tombstones; picking Deleted is the only way to see them.

## 3. Attribution comes from one query

`select("*, uploader:profiles!documents_uploaded_by_fkey(...), editor:...")`.
One round trip, and RLS still decides — which only works at all because 5.3
widened the profile directory to teachers.

**Uploaded by and Updated by share a column when they are the same person**,
as you asked. The rule sits in `DocumentPeopleCell`, so the table body cannot
drift from it.

## 4. Actions

A `DropdownMenu` per row: **Edit** (a dialog, TanStack Form + Zod), **Archive**
or **Restore**, **Delete**. Retry stays on failed rows, and preview stays on
the name.

**Archive and Delete both confirm, in an `AlertDialog` with a title and a
description that says what will actually happen** — that archiving takes the
document out of the assistant's reach while keeping the PDF, and that deleting
removes the file for good. `AlertDialog` rather than `Dialog`: it traps focus
on the destructive choice and does not close on a click outside, which is the
difference between confirming and dismissing.

Restore is not confirmed. It is the undo.

## 5. Six badges

`Badge` variants, coloured by what a teacher needs to notice: Ready is
`verified` green, Failed and Deleted are `lacquer`, Uploading and Indexing are
`pending` amber, Archived is muted — deliberately the quietest, because an
archived document is not a problem, it is a decision.
