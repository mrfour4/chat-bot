---

## Shape

`POST /api/documents` already creates a `pending` row. This phase adds, in the
same request:

```
markIndexing → uploadToFileSearchStore → poll → post-index check
             → markReady(geminiDocumentName)   or   markFailed(reason)
```

**60s cap**, roughly 4× the slowest run measured in 2.1.0 (10.0–14.6s). If the
cap is hit, the row is marked `failed` with a message saying so, rather than
left in `indexing` forever — a `failed` row is honest and 2.1.8 can retry it,
whereas a stuck `indexing` row is a lie the UI will happily poll on.

---

## The post-index check is the point of this phase

2.1.0 established there is **no metadata field that reveals an empty index**:
`sizeBytes` reports raw uploaded bytes, and `state` reads `STATE_ACTIVE`
regardless. So after the operation completes we run one scoped retrieval:

```ts
tools: [{ fileSearch: {
  fileSearchStoreNames: [store],
  metadataFilter: `documentId=${id}`,   // syntax confirmed in 2.1.0
} }]
```

Zero `groundingChunks` → **`failed`**, not `ready`.

Without this, a document that indexed to nothing would sit in the list marked
*Sẵn sàng*, and every question about it would answer "không có trong tài liệu
hiện có" — indistinguishable from our refusal working correctly. That is the
one failure mode this product cannot afford, because nothing about it looks
wrong.

It costs one extra model call per upload. On a free tier that is worth knowing
about, and it is still the right trade: it is paid once at upload, not per
question, and it converts a silent lie into a visible failure.

## Interface

```ts
// src/lib/documents/indexer.ts
export const INDEXING_TIMEOUT_MS = 60_000;

export type IndexOutcome =
  | { ok: true; geminiDocumentName: string; chunkCount: number }
  | { ok: false; message: string };

export async function indexDocument(input: {
  documentId: string;
  fileName: string;
  bytes: Uint8Array;
}): Promise<IndexOutcome>;
```

Returns rather than throws: every failure here is expected operational
weather — a timeout, a 503, an unreadable file — and the caller's response to
all of them is the same `markFailed`. `describeError` (2.1.3) turns the
unexpected ones into something a teacher can read.

`customMetadata` is stamped as `[{ key: "documentId", stringValue: id }]` —
the array shape corrected in 2.1.0 — which is both what makes the scoped check
possible and what lets 2.2.2 resolve a citation back to a row.

## Three findings, each from something going wrong

### 1 · `metadataFilter` only matches lowercase metadata keys

The first run failed everything with zero chunks, while an unfiltered query
returned 4 chunks from both documents — so indexing was fine and the *filter*
was broken. One upload carrying three keys settled it:

| stored key | filter | chunks |
| --- | --- | --- |
| `docid` = `uitpage1` | `docid=uitpage1` | **2** ✅ |
| `documentId` = `uitpage1` | `documentId=uitpage1` | **0** ❌ |
| `documentId` = `uitpage1` | `documentid=uitpage1` | **0** ❌ |
| `hyphenated` = `a-b-c` | `hyphenated=a-b-c` | **2** ✅ |

Same document, same value. **The uppercase letter in the key is what breaks
it** — and lowercasing the *filter* does not rescue a key stored in camelCase.
Hyphens in values, the original suspect, are entirely fine.

Nothing in the docs or the SDK types says this. The key is now
`DOCUMENT_ID_KEY = "docid"`, exported, because 2.2.2 reads the same key back to
resolve citations and the two must not drift.

**This is the failure mode that motivated the post-index check, arriving in our
own code.** Had `indexDocument` marked documents `ready` without verifying
retrieval, every upload would have looked successful and every answer would
have been ungrounded.

### 2 · Two orphan paths, both real

Uploading and verifying are separate operations, so the second failing does not
undo the first. Both `ok: false` paths after a successful upload were leaving a
document in the store with nothing in Postgres pointing at it — invisible to
the teacher, undeletable through the UI, still occupying quota.

Confirmed rather than theorised: after the failed runs, the store held two
orphans. Fixed by tracking the uploaded name outside the `try` and discarding on
every failure path, including the `catch`.

### 3 · The free tier is 20 requests per day, per model

```
Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests
limit: 20, model: gemini-3.6-flash
quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier
```

Twenty `generateContent` calls per model per day. Not per minute. This is a
project-level constraint, recorded as §5.14 — see there for what it changes.

`gemini-2.5-flash` is not an escape route: it now 404s with *"no longer
available to new users… use models/gemini-3.6-flash"*. That is Google pointing
at the model **D7** should probably settle on.

### A note on how check 3 failed

The scoping check returned zero chunks moments after the same filter had worked
inside `indexDocument`. The most likely explanation is quota pressure: the model
answered without running the retrieval tool. If so, it is reassuring —
§5.7 layer 3 treats missing grounding as a refusal, so the degraded mode is a
refusal, not a fabrication. Worth confirming deliberately in 2.2.1 rather than
assumed.
