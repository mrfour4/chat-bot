# 9.4 — Changing a password, or setting a first one

## Two different situations

| The account has | Sees | Why |
|---|---|---|
| a password (`email` identity) | current password + new password | changing it must prove it is you |
| no password (Google only) | new password alone | there is nothing to prove against |

`hasPassword(identities)` decides, from `auth.identities` — the same list 9.6
uses. A Google-only account is told plainly why the form looks different: *"Tài
khoản này đang đăng nhập bằng Google và chưa có mật khẩu."* Setting one is
additive; it gives a second way in without disconnecting anything.

## The current password is not decoration

`secure_password_change` is `false`, so `supabase.auth.updateUser({ password })`
would accept a new password on the strength of the session alone. Anyone with a
borrowed laptop or a stolen cookie could lock the real owner out of their own
account without ever knowing the old password.

So `changePassword` re-authenticates first:

```ts
const { error: wrongPassword } = await supabase.auth.signInWithPassword({
    email: user.email,
    password: parsed.data.currentPassword,
});

if (wrongPassword) return { error: t("currentPasswordWrong") };
```

The alternative was flipping `secure_password_change` on, which makes Supabase
demand a reauthentication nonce sent by email — a second email in a flow that
does not need one. Checking the old password is the same guarantee, in one
round trip, with no mail involved.

`setPassword` deliberately does **not** do this: there is no old password, and
the session was established by Google or by a recovery link that was itself
proof of email ownership.

## Small refusals that prevent confusing successes

`changePasswordSchema` refuses `newPassword === currentPassword`. Supabase
accepts that happily and reports success, having changed nothing — a message
that says "password changed" when it was not is worse than an error.

The new password is held to `MIN_PASSWORD_LENGTH`, the same constant sign-up
uses, so the rule cannot drift between the two places a password is chosen.

## Errors are ours, not the SDK's

`updateUser` failures return `t("passwordRejected")` rather than
`error.message`. Supabase's message is English, sometimes mentions internals,
and this app is Vietnamese-first. The earlier draft of this action passed
`error.message` straight through; that would have been the only English string
on an otherwise Vietnamese page.
