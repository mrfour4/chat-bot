# 6.13 — The refetch loop, again — and the chat input

## What you asked

> Please verify again that the old-message refetch bug is fixed. It should not
> continuously fetch older messages until there are no messages left.

I checked, and **it was not fixed**. 6.11 fixed the mount-time double fetch —
two requests with one cursor, which is what produced the duplicate-key error —
but not the chain, and you would have seen it again on a long conversation.

## Why 6.11 was not enough

The trigger asked a question about *state*: "is the viewport at the top?"

```ts
if (armed && hasOlder && !start && !loading) onReach();
```

Follow one successful page through:

1. The reader scrolls to the top. `start` is `false`. A page is requested.
2. It arrives. `onSuccess` sets the cursor, prepends the messages, and asks for
   the scroll to be restored.
3. React re-renders and runs the effect again — `loading` is now `false` and the
   cursor has changed, so the dependencies changed.
4. **`start` is still `false`.** The scroll position has not been restored yet:
   the scroller does that from a MutationObserver, and my own
   `scrollToMessage` runs in an animation frame. The effect body reads the value
   from the render that has already happened.
5. So it fires again. And again for the next page, one round trip at a time,
   until the conversation is exhausted.

The single-flight ref from 6.11 does not stop this — each fetch has a *different*
cursor, so it is not a repeat. `prependMessages` does not either: the messages
are all genuinely new, so no duplicate key appears. Those two fixes were right
about what they fixed and blind to this.

## The change: a transition, not a state

The question is now "did the reader just *arrive* at the top?" — which the
previous value answers, and which does not depend on when the scroll restoration
lands:

```ts
const reachedTop = previousStart !== false;
const cannotScroll = !end;
return reachedTop || cannotScroll;
```

After a page lands, `previousStart` is already `false`, so step 5 does not fire.
The restore then sets `start` to `true`, and only scrolling back up sets it
`false` again — one page per deliberate scroll.

`cannotScroll` keeps the one case the transition rule would strand: a
conversation whose messages do not fill the viewport has no top to arrive at, so
it fills itself until it does, or until there is nothing older.

The decision is a pure function, so this is checked rather than argued:
`shouldLoadOlder` has eight tests, and the one named *"does not load again just
because the viewport still reads as the top"* is the bug above. Reverting to the
state-based check fails it.

## The input

`autoComplete="off"` on both the form and the input, since every question is
different and the browser's saved list is noise. `autoCorrect="off"` and
`spellCheck={false}` go with it: an English-locale browser underlines most
Vietnamese words, and iOS autocorrect rewrites diacritics.

## Verify

- Open a conversation with several pages, scroll to the very top: **one** page
  loads, and the loading pill disappears. Nothing else loads until you scroll up
  again.
- Repeat to the beginning: one page per arrival, no runaway.
- The question box offers no autocomplete dropdown and no red underlines.
