# 4.6 — Mutations report their outcome

**Goal.** Every mutation says whether it worked.

---

## The Toaster was never mounted

`toast.tsx` had been installed at some point and was wired to nothing — no
`Toaster` in `providers.tsx`, no call sites. That is the actual reason no
action in this app had ever confirmed itself. It is mounted now, inside the
query provider.

## One wrapper, two shapes

`src/lib/notify.ts` exports `notifySuccess` and `notifyError`. A wrapper rather
than `toast.add` at each site, because these two are the only shapes this app
should produce, and going through them stops a success arriving styled as an
error because a `type` string was mistyped.

## Where a toast is the right feedback, and where it is not

The rule this phase settled on: **a toast reports an outcome the screen does
not already show.**

| Mutation | Success | Failure |
| --- | --- | --- |
| Upload | toast | toast |
| Delete | toast | toast |
| Retry indexing | toast | toast |
| Ask a question | **no toast** | toast **and** inline |
| Sign in / sign up | redirect or inline notice | toast **and** inline |

**No success toast for a question.** The answer appearing is the feedback. A
toast saying "answered" would be a second notification of something already on
screen and in the reading position.

**A failed question keeps its inline message as well.** A toast expires. A
question with no answer and no explanation looks like it was ignored — the same
confusion this project keeps designing against.

**The upload form's inline error is gone.** With a toast on failure it was the
same sentence twice, two inches apart.
