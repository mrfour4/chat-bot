# 5.6 — Many files at once, indexed one at a time

**Goal.** Choose several PDFs and upload them together. Index them in
sequence, because the free tier is not a place to find out whether parallel
works.

---

## 1. One request, one summary

The form takes `multiple`; the route reads every `file` entry from the
`FormData` and answers with **one result per file**:

```json
{ "results": [
  { "fileName": "uit.pdf",  "outcome": "queued",    "document": { … } },
  { "fileName": "iuh.pdf",  "outcome": "duplicate", "message": "…" },
  { "fileName": "notes.rtf","outcome": "rejected",  "message": "…" }
] }
```

Per-file outcomes rather than a single status, because the interesting case is
the mixed one — four PDFs of which one is a duplicate and one is not really a
PDF. A 400 for the whole batch would throw away three good uploads; a 201 for
the whole batch would hide two problems.

Each file is validated, checksummed and stored on its own, so one bad file
cannot stop the others. The toast reports the counts and the rejected ones keep
their own reasons.

## 2. Sequential indexing

Uploading no longer schedules a job per document. It schedules **one worker**,
which drains the queue:

```
claim the oldest pending document with a stored PDF
  index it
  repeat until nothing is pending, or the time budget runs out
```

The claim is 3.6's atomic one (`.eq("status", "pending")` on the transition),
so this is safe even if two workers start — which is the point: correctness
does not depend on there being exactly one.

**Sequence is enforced twice**, in two different ways, because the two failure
modes are different:

- **In-process**, a module-level promise means a second `after()` on the same
  server joins the running worker instead of starting a second one. This is
  what keeps a five-file upload from making five concurrent Gemini calls.
- **In the database**, the claim means that if a second instance does start a
  worker — a second region, a redeploy mid-batch — the two cannot both index
  the same document.

The in-process lock is not durable and is not pretending to be. It is a
politeness that saves quota; the claim is the correctness.

**A document that fails to claim is remembered and skipped**, or the worker
would spin on the same row forever: `nextPending` returns the oldest, the claim
loses the race, and without the skip list the next iteration asks for the same
oldest row again.

## 3. The time budget

`after()` work lives inside the request's function lifetime, so the worker stops
at four minutes and leaves the rest `pending`. The sweeper (3.6) re-drives them
on the next page load or cron tick.

Four minutes and not more because `maxDuration` is 300: the budget has to end
before the platform kills the function, or the last document is left claimed as
`indexing` by a worker that no longer exists — which is exactly the state
`STALE_AFTER_MS` exists to recover, but slowly and only after five minutes of
looking stuck.

## 4. What the mock server makes visible

With `MOCK_GEMINI_FAILURE_RATE=1`, uploading five files now shows the thing
worth watching: they move through Uploading → Indexing one at a time, some
land on Ready and some on Failed with their own reason, and the row updates
arrive by broadcast without a poll.

---

## Checks

- five files: five rows, indexed one after another, never two `indexing` at once
- a rejected file does not prevent the others being queued
- a duplicate reports as a duplicate and does not create a second row
- the queue stops at the budget and the sweeper finishes the rest
- typecheck · lint · test · build
