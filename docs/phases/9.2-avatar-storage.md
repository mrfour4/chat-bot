# 9.2 — Where an avatar lives

## The bucket

`avatars`, private, 2 MiB, `image/png | image/jpeg | image/webp` — the same shape
as `documents`, for the same reason. An avatar is a photograph of a student;
a permanent public URL is not something to hand out by default. Nothing reaches
an object without a policy or a signed URL the server mints.

One difference from `documents`, and it is deliberate: there, **any** teacher may
read **every** file, because a teacher managing the library needs to open a PDF
somebody else uploaded. Here, an object is readable only by the person it belongs
to. Everyone else sees an avatar through a signed URL that the server produces on
their behalf, never by reading the object.

Ownership is carried by the path, `<user_id>/avatar.<ext>`, and the policies
compare `(storage.foldername(name))[1]` to `auth.uid()` — the same convention
`documents` uses, so the rule is legible in the policy rather than depending on
which client performed the upload.

All four verbs get a policy. `UPDATE` is not optional even though nothing
"edits" an image: replacing an avatar is an **upsert**, and Supabase upsert needs
INSERT + SELECT + UPDATE. Missing one fails as a policy violation that names
nothing useful — this cost time in 2.1 and did not need to cost it again.

## One stable filename per user

`avatarPath()` returns `<user_id>/avatar.<ext>`, not a timestamp or a random id,
so replacing a picture overwrites the previous object instead of accumulating one
file per change. Since the extension follows the *detected* format, changing from
a PNG to a JPEG does leave the old object behind — so the upload action lists the
folder afterwards and removes anything that is not the file it just wrote.

## The bytes decide the format, not the filename

`File.type` is derived from the extension by the browser, so it is a hint from
whoever chose the filename. `detectImageType` reads the signature instead:

| Format | Signature |
|---|---|
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| JPEG | `FF D8 FF` |
| WebP | `RIFF` at 0 **and** `WEBP` at 8 |

WebP needs both markers because `RIFF` alone is a container, not a format — a
`.wav` file starts with exactly the same four bytes. There is a test for that
specific confusion.

Where the declared type and the bytes disagree, the bytes win and the file is
stored under its real type: a genuine JPEG named `.png` is saved as a JPEG rather
than refused. What *is* refused is a file whose bytes are not an image at all —
`4D 5A` (a Windows executable) named `avatar.png` with `File.type` obligingly
reporting `image/png`.

Two gates, one in the app and one in the platform: even if `validateAvatar` were
bypassed, the bucket's `allowed_mime_types` would reject the object. The same
reasoning as `%PDF-` in 2.1.2.
