# 5.5 — Status without polling

**Goal.** When a document finishes indexing, the row changes because the
database said so, not because the browser asked again.

---

## 1. Supabase Realtime, not a webhook

You asked for a webhook or an existing solution. A webhook is the wrong shape:
it delivers to a *server*, and the thing that needs to know is a *browser* —
possibly several, on a page that may have been open for ten minutes. We would
have to build the second half, server to browser, ourselves. That is the
complicated mechanism you asked to avoid.

Supabase Realtime is already in the stack. No account, no keys, no third party,
and it authenticates with the session the page already has.

## 2. Broadcast from Database, not Postgres Changes

Both work. Broadcast is Supabase's own recommendation, and the difference that
matters here is **where authorization happens**: Postgres Changes evaluates the
table's RLS policy against every event for every subscriber, while Broadcast
checks one policy on `realtime.messages` when the channel is joined.

```sql
create trigger documents_broadcast_change
  after insert or update or delete on public.documents
  for each row execute function public.documents_broadcast_change();

create policy "documents_changes_readable_by_teachers"
  on realtime.messages for select to authenticated
  using ((select realtime.topic()) = 'documents' and public.is_teacher());
```

The topic check is not optional. `realtime.messages` is shared by every channel
in the project, so a policy that only asked `is_teacher()` would open all of
them.

Verified against hosted: a teacher's private channel receives `INSERT`,
`UPDATE`, `UPDATE`, `DELETE` in order, and a guest is refused by name —
*"Unauthorized: You do not have permissions to read from this Channel topic"*.

**No `setAuth()` call is needed in the app.** `supabase-js` ties the socket's
token to the auth state itself, on `INITIAL_SESSION`, `SIGNED_IN` and
`TOKEN_REFRESHED` — read from `_handleTokenChanged`, not assumed.

## 3. The mistake that shaped this phase

Postgres Changes was built first and measured as **delivering INSERT and DELETE
while silently dropping every UPDATE** — three consistent runs on hosted, and
working locally. That is a compelling signal, and it is wrong.

The probe signed in on the **service-role client**, which replaces that
client's token. Every write after that line ran as the teacher, and
`documents_update_teacher`'s `WITH CHECK` refuses an update that does not set
`updated_by` — so the UPDATEs never happened. There was nothing to deliver.

It survived so long because the probe ignored the returned `error`. It was
found by printing it. Two lessons worth keeping:

- **`signInWithPassword` mutates the client it is called on.** A test that
  needs both a privileged writer and a signed-in reader needs two clients.
- **A consistent result is not a correct one.** Three runs agreed because they
  repeated the same broken setup three times.

The migration carries this note, because the next reader will otherwise find a
choice with no reason attached and a rationale that was never true.

## 4. The payload is a signal, not data

The subscription invalidates the documents query; it does not patch the
broadcast row into the cache.

The table is paged, searched and filtered server-side, so a changed row may
belong on a page nobody is looking at, may have just left the current filter,
or may need to enter it. Merging the payload would mean re-implementing the
query's `where` clause in the browser, where getting it wrong puts a document
in the wrong list rather than raising an error. Invalidating asks a question
that already has a correct answer.

## 5. A dead socket must not look like a stuck document

Polling is not deleted, it is demoted. `useDocumentsRealtime` reports whether
the channel is actually `SUBSCRIBED`, and `useDocuments` polls **only when it
is not**, and only while something is in flight.

A WebSocket fails in ways a fetch does not: a proxy that strips upgrades, a
captive portal, a suspended tab. Every one of those would otherwise render as a
document stuck on "Uploading" forever — §5.12's rule again, that a broken
connection and a slow index must not look the same.

Turning polling off entirely would have been the smaller diff and the worse
product.

## Checks

- teacher's channel receives INSERT, UPDATE, UPDATE, DELETE in order (hosted)
- a guest is refused the topic by name
- the channel reports `SUBSCRIBED`; without it, polling resumes
