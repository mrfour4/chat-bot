# 9.10 — After a reset, sign in again

## What you asked for

> After the password has been successfully reset, please redirect the user back
> to the login page instead of automatically signing them in.

## Why it was not simply "make setPassword sign out"

`setPassword` serves two situations that look identical and are not:

| Situation | Where | What should happen after |
|---|---|---|
| recovering a forgotten password | `/profile/password`, reached from an email | sign out, back to `/login` |
| a Google-only account setting a **first** password | `/profile`, while signed in | stay exactly where you are |

The second case is someone managing their account mid-session. Signing them out
would throw them off the page they were using, to prove a point about a password
they never lost. So the sign-out belongs to the recovery path alone.

`completePasswordReset` is that path: update, `signOut`, then
`redirect("/login?notice=password-reset")`. `setPassword` is unchanged.

`SetPasswordForm` now takes its action as a prop, so one component serves both
pages and the decision lives where the difference is — the page — rather than in
a `mode` flag the form would have to interpret.

## Why signing out is the better behaviour anyway

A recovery link is proof that someone can read the mailbox, which is a weaker
claim than knowing the password. Ending the session means the new password is
used at least once by whoever set it, and it leaves nothing behind on a shared
or borrowed device — the exact situation a password reset often follows.

## The login page says why they are there

Arriving back at a login form with no explanation reads as a failure. `?notice=`
carries a success message, rendered as a plain (not destructive) alert:

> Đã đổi mật khẩu. Vui lòng đăng nhập bằng mật khẩu mới.

`loginNoticeKey` maps the value, returning `null` for anything unrecognised, so a
crafted query cannot choose arbitrary copy — the same shape as `loginErrorKey`,
including tests for `toString` and `__proto__`. Verified:

```console
?notice=password-reset       alerts=1
?notice=bogus                alerts=0
<none>                       alerts=0
```

## Verified end to end

```
1. recovery session:      lqtu12369@gmail.com
2. set new password:      ok
3. signed out
4. session afterwards:    none -- must sign in again
5. old password:          refused
6. new password:          works
```

Step 4 is the one this phase adds; 5 and 6 confirm it did not come at the cost of
the reset itself. The test account's password is back to `test-password-1` and
the Mailpit inbox is cleared, so your own run starts from a clean state.
