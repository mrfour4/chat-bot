# 9.9 — Testing password recovery without an email quota

## The limit cannot be raised on hosted

You asked for a high limit while testing. Tried it: `email_sent = 200`, pushed —
and the CLI reported `auth: up_to_date`, meaning it never sent the value. The
setting's own comment in `config.toml` says why:

> Number of emails that can be sent per hour. **Requires auth.email.smtp to be
> enabled.**

Which matches the documentation exactly: *"2 emails per hour with the built-in
email provider. You can only change this with a custom SMTP setup."* There is no
way to raise it on hosted while the built-in provider is in use — not through the
CLI, not through the Dashboard.

Locally it takes effect immediately, because Mailpit is the mail server and has
no opinion about volume:

```console
GOTRUE_RATE_LIMIT_EMAIL_SENT=360000
```

So the app is pointed at the **local stack** for testing. The hosted values are
kept in `.env.local`, commented, immediately above the local ones — switching
back is uncommenting three lines and restarting `next dev`.

## Verified end to end, through the running app

```
1. request reset:          accepted
2. email arrived:          Reset your password -> lqtu12369@gmail.com
3. link lands on:          /auth/callback?code=…&flow=recovery&next=/profile/password
4. exchange:               ok, session for lqtu12369@gmail.com
5. set the new password:   ok
6. old password refused:   yes
7. new password works:     yes
```

Steps 6 and 7 are the ones that matter: a reset that leaves the old password
working has not reset anything, and neither has one whose new password does not
let you in.

## Two things to know while testing locally

**The email is in English.** The Vietnamese template is still commented out in
`config.toml`, because leaving it enabled makes `config push` fail for the whole
file on a free-tier project (9.6). Uncomment it for local-only work if you want
to see the real copy.

**`listUsers` fails on this database.** The admin API scans every `auth.users`
row, and rows inserted by SQL — the RLS fixtures, the Google probe in check 29 —
have `NULL` token columns where GoTrue expects `''`:

```
list failed: Database error finding users
```

Look a user up in `public.profiles` and call `updateUserById` with the id
instead. This is the same fault that made a recovery request 500 in 9.5; it is
worth knowing that it also breaks admin listing, not just email flows.

## Before real use

`email_sent = 200` is marked TEMPORARY in `config.toml` and must come down. A
high limit turns a public reset form into a way to flood somebody's inbox — the
form takes any address and sends mail to it, so the rate limit is the only thing
standing between a stranger and a hundred emails an hour to a victim.

The proper fix is custom SMTP, which lifts the ceiling honestly and also unblocks
the Vietnamese template. Resend's free tier is 3,000 a month; Dashboard →
Authentication → SMTP Settings, then set `email_sent` to something like 30 and
push.
