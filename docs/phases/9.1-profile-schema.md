# 9.1 — Somewhere safe to write a profile

## What the feature needs, and what that nearly cost

A profile page has to write two fields: `full_name` and a new `avatar_url`.
`public.profiles` had no UPDATE policy at all, and the init migration says why:

> profiles: read your own row. No UPDATE policy at all, so a user can never
> promote themselves to teacher through the client.

RLS was carrying that guarantee by itself. Underneath it, the grants tell a
different story:

```
authenticated | UPDATE | role
authenticated | UPDATE | email
authenticated | UPDATE | id
```

`authenticated` may update **every column**. Adding the one UPDATE policy this
feature needs would have made `update profiles set role='teacher'` a two-line
PostgREST request for any signed-in student. The policy was not the protection —
its *absence* was.

## Three brakes, not one

| # | Mechanism | Refuses with | Survives |
|---|---|---|---|
| 1 | column grant: `grant update (full_name, avatar_url)` | `42501` before RLS is consulted | someone adding a second policy |
| 2 | policy `profiles_update_own`, USING **and** WITH CHECK | 0 rows | someone widening the grant |
| 3 | trigger `profiles_guard_immutable` | `P0001` | someone doing either of the above |

Brake 1 alone would do today. Brake 3 exists because `grant update on profiles`
is a plausible future edit — a hurried fix for some unrelated permission error —
and it must not silently reopen self-promotion.

`revoke` comes before `grant update (cols)`, because a column grant **adds to**
a table-level grant rather than replacing it. Without the revoke, all three
brakes would have been installed around a door that was still open.

## The bug this caught before shipping

The first version of the guard trigger refused *every* role change. That breaks
the only way to grant the teacher role:

```console
SERVICE_ROLE_PROMOTE: BLOCKED [P0001] profiles.role is granted by an admin, not by the user
```

`npm run promote:teacher` runs under the service role. The trigger now returns
early when `auth.uid()` is null — the same test `documents_stamp_updated_by`
uses to tell a person from a background job:

```console
SERVICE_ROLE_PROMOTE: allowed
```

An admin is not a user, and only users need guarding.

## What a student can and cannot do

Probed as a real `authenticated` identity, in a rolled-back transaction:

```
RENAME_SELF:   allowed, 1 row(s)
SET_AVATAR:    allowed, 1 row(s)
SELF_PROMOTE:  BLOCKED [42501] permission denied for table profiles
CHANGE_EMAIL:  BLOCKED [42501] permission denied for table profiles
RENAME_OTHER:  allowed, 0 row(s)
```

`RENAME_OTHER` is the interesting line: no error, no rows. RLS filters rather
than refuses, which is the correct shape — it does not tell an attacker whether
the row exists.

`email` is immutable here on purpose. It mirrors `auth.users.email`, and letting
the copy drift from the source would be worse than not offering the feature.
Changing an email is `supabase.auth.updateUser`, which re-verifies it.

## An existing test asserted the weaker guarantee

Check 6 has always claimed "student cannot self-promote to teacher". It ran the
UPDATE bare and inspected the row afterwards, which worked when the update
silently affected no rows. With a column grant it *raises*, so the unhandled
`42501` aborted the entire DO block — 33 checks became 1.

Check 6 now accepts either refusal, `42501` or `P0001`, because its question is
"was it refused" and not "by which brake". Check 33 is the one that names the
trigger.

## Tests, and what breaks them

Checks 30, 32, 33, 34 added; check 6 rewritten. **33 passed, 0 failed.**

| Change | Result |
|---|---|
| drop `profiles_guard_immutable` | check 33 fails — *nothing stopped the promotion* |
| `grant update on profiles` (trigger kept) | all pass — correct, the trigger refuses |
| drop `profiles_update_own` | checks 30 and 33 fail |
| guard every caller, not just users | check 34 fails — *promote:teacher would fail* |

Check 33 lives **outside** the main DO block, and that placement is load-bearing:
a `GRANT` issued inside a PL/pgSQL block is not in effect for later statements of
that same block, so the attempt failed on the column grant and never reached the
trigger — the check tested the wrong brake and passed for the wrong reason.

Two harness mistakes worth recording, because both produced false confidence:
the first version of this migration was pushed as an **empty file** (a heredoc
that never landed) and `db push` recorded it as applied, so every probe reported
the pre-migration behaviour; and the first falsification run used a shell
variable holding the psql command, which zsh does not word-split, so all four
"falsifications" silently changed nothing and the suite "passed" untouched.
