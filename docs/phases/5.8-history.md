# 5.8 — History: search, rename, delete, and a list that does not grow

**Goal.** Find a conversation, rename it, delete it, and scroll a thousand of
them without the page getting heavier.

---

## 1. Why TanStack Virtual here and not in chat

5.7 found that `MessageScroller` virtualizes by itself, so chat needed nothing.
History is the opposite case: a plain list, uniform rows, no scroller written
for it. `useVirtualizer` is the right tool and this is where it earns its place.

**There is no official TanStack Virtual skill.** `npm pack` then `tar tzf` on
`@tanstack/react-virtual@3.14.10` finds no `skills/` directory — unlike
react-table, which ships six. So the API came from the installed
`dist/esm/index.d.ts` and `@tanstack/virtual-core`'s option list, the same way
Query and Form were handled.

The parts used: `count`, `getScrollElement`, `estimateSize`, `overscan`,
`getItemKey`, and `measureElement` on each row so a two-line title measures
itself rather than being assumed.

**Rows are measured, not fixed.** A conversation title wraps to two lines at
narrow widths, and `estimateSize` is only the first guess; without
`measureElement` the list would drift further out of position the further you
scrolled — a bug that looks like the scrollbar lying.

## 2. Cursor paging, and why it differs from documents

You asked for cursor paging here and **page numbers on the documents table**,
and those are the right way round for a reason worth writing down:

- A teacher looking for a document wants to *navigate* — page 4, back to page
  2, filter and start again. Numbered pages answer "how many are there".
- A student scrolling their history wants to *continue*. There is no page 4 of
  your own conversations; there is only further back. A cursor also cannot
  skip or repeat a row when a new conversation is created mid-scroll, which
  offset paging does.

Same keyset as 5.7 — `(created_at, id)` — for the same reason: several
conversations can share a timestamp.

## 3. Fetching before the end, not at it

The list asks for more when the **last rendered virtual item** is within the
final few rows, not when the scrollbar hits the bottom. Waiting for the bottom
means the reader always sees the end of the list and then a spinner; asking a
few rows early means the next page is usually already there.

This is why the trigger is derived from `virtualItems.at(-1)?.index` rather
than a scroll listener: the virtualizer already knows what is rendered, and a
second source of truth about scroll position would be one more thing to keep
in step.

## 4. Search

`ilike` on the title, wildcards escaped, debounced at 300ms — the same helper
the documents table uses, because a search that behaves differently on two
pages of one app is a bug that is hard to see and easy to write.

An untitled conversation is matched by nothing, and there is no way to write
that in a query. It is a real hole: a conversation whose first question failed
has no title. Titles are derived from the first question (2.3.4), so this only
affects conversations that never got an answer — and those are the ones with
nothing to find anyway.

## 5. Rename and delete

`PATCH` and `DELETE` on `/api/conversations/[id]`, both going through the
user's own client so **RLS decides**, and both answering 404 rather than 403
for someone else's conversation, matching 3.5.

Deleting a conversation deletes its messages, by `on delete cascade` in the
original schema. It is confirmed in the same `AlertDialog` the documents table
uses, and the description says how many messages go with it — a count is the
one thing that makes this decision different from deleting a document.

## Checks

- 60 conversations: the DOM holds a screenful, not 60
- scrolling near the end loads more, without a jump
- search narrows to the right rows and survives a `%` in the term
- rename shows immediately and survives a reload
- delete asks first, says what goes, and removes the messages too
- another user's conversation is 404 to both verbs
