## 1 · Classify the failure

`src/lib/gemini/errors.ts`:

```ts
export type GeminiFailure = {
  kind: "quota" | "unavailable" | "other";
  retryable: boolean;
  retryAfterMs: number | null;
  message: string;   // Vietnamese, for the teacher
  detail: string;    // the original, for logs
};

export function classifyGeminiError(error: unknown): GeminiFailure;
```

The SDK throws with a JSON string as its message, so this parses it and reads
`error.code`, `error.status`, and the `RetryInfo` detail carrying `retryDelay`.
It must never throw itself — a parser that fails while explaining a failure is
worse than useless, so anything unexpected falls through to `other`.

**The messages:**

| kind | shown |
| --- | --- |
| `quota` | "Đã hết hạn mức Gemini cho hôm nay (gói miễn phí cho phép 20 lượt/ngày với mỗi mô hình). Tài liệu chưa được lập chỉ mục — hãy thử lại sau khi hạn mức được đặt lại." |
| `unavailable` | "Máy chủ Gemini đang quá tải. Vui lòng thử lại sau ít phút." |
| `other` | `describeError`'s output, as today |

The quota message names the actual limit, because "quota exceeded" without a
number leaves you unable to tell a misconfiguration from a plan ceiling. That
sentence is the difference between the teacher filing a bug and the teacher
waiting.

## 2 · Retry, but frugally

Retrying a **quota** error mostly spends the quota that is already gone, so it
is retried **at most once**, and only when the API's own suggested delay is
under 10 seconds. A **503** is genuinely transient and gets up to 3 attempts.

The API tells us how long to wait, so we use its number rather than inventing
a backoff curve.

## 3 · Retry from the UI

`POST /api/documents/[id]/retry` — teacher-only, only for a `failed` row.

The upload is already stored in Postgres by checksum, but **not the bytes** —
we deliberately do not keep the PDF (§5.10). So retry cannot re-index on its
own; it needs the file again. Rather than pretend otherwise, a `failed` row
offers **"Tải lên lại"**, which re-opens the file picker for that document and
reuses the existing row.

That is more honest than a retry button that would fail for a reason the
teacher cannot see. **It also means the route is thin**: it clears the failure
so the row can be re-attempted, and the existing upload path does the rest —
with the duplicate check skipped for this row, since re-uploading the same
bytes is the entire point.

### One simplification, found while building

The plan called for `POST /api/documents/[id]/retry`. **It is not needed.**

Retry always requires the file again, because we deliberately do not keep the
PDF bytes (§5.10). So the retry mechanism *is* re-uploading — and the upload
route already does every step correctly. The change is three lines: a duplicate
is rejected only when the existing row is **not** `failed`; a failed row is
reused instead of duplicated.

That removes an endpoint, removes the chance of two indexing paths drifting
apart, and means the checksum stays a genuine unique key rather than something
retry has to work around. The row keeps its identity and history; only its
status changes.

### Retry budgets, deliberately asymmetric

- **503 · unavailable** — up to 3 attempts. A genuine capacity blip.
- **429 · quota** — one retry, and only if the API's suggested delay is under 10s. Retrying a daily quota mostly spends quota that is already gone.
- **anything else** — no retry. A corrupt PDF will still be corrupt.

The wait comes from the server's own `RetryInfo.retryDelay` rather than an
invented backoff curve.
