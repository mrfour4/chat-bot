# 6.17 — Vietnamese characters in KaTeX

## What you reported

> `No character metrics for 'ể' in style 'Main-Regular' and mode 'text'`

## What the warning actually means

Not a missing font. `getCharacterMetrics` looks the character up in
`fontMetricsData`, and when it finds nothing, `makeSymbol` does this
(`katex.mjs`):

```js
console.warn("No character metrics for '" + value + "' …");
symbolNode = new SymbolNode(value, 0, 0, 0, 0, 0, classes);
```

Height 0, depth 0, **width 0**. The glyph is still drawn by the browser, but
KaTeX lays it out as occupying no space, so everything after it is positioned as
if it were not there. The console warning was the visible half of a layout bug.

## Why KaTeX misses exactly these characters

It does not miss them all, which is the useful part. Three tiers, verified by
rendering each and counting warnings:

| Characters | Where | Result |
|---|---|---|
| `à é î õ ü` | Latin-1 | **fine** — `symbols.js` maps them to real glyphs KaTeX ships |
| `Đ đ Ơ ơ Ư ư ă` | Latin Extended-A/B, `0x0100–0x024F` | **no warning** — in `scriptData`'s `latin` block, so `getCharacterMetrics` substitutes `M`'s metrics |
| `ể ộ ấ ằ ợ …` | Latin Extended **Additional**, `0x1E00–0x1EFF` | **broken** — in no `scriptData` block, so no substitution and no metrics |

That third block is where almost every toned Vietnamese vowel lives. KaTeX's
`scriptData` covers Cyrillic, Armenian, Brahmic, Georgian, CJK and Hangul, and
Latin only as far as `0x024F`. Vietnamese falls in the gap.

## The fix

KaTeX already has the right behaviour for a character it cannot measure — borrow
`M`'s metrics — it just does not apply it here. `katex.__setFontMetrics`, its
documented escape hatch, lets us extend each font's table before anything
renders, deriving each entry from the character's own NFD decomposition:

- **width, italic, skew** from the base letter, so `ể` advances like `e`. This is
  better than KaTeX's own fallback, which would give it the width of `M`.
- **height** = cap height when the decomposition has a mark above.
- **depth** = a descender's depth when it has a mark below, which is what makes
  room for the dot under `ộ`, `ụ`, `ị`.

134 codepoints, generated rather than listed, so a letter I forgot is still
covered.

## Two things I tried first

**NFD normalisation before rendering.** `"ể".normalize("NFD")` is `e` + two
combining marks, all three inside KaTeX's supported ranges — which looked like a
fix with no patching at all. It fails: KaTeX parses combining marks as accent
commands and throws `Unknown accent`, turning the whole formula red. The probe
took two minutes and saved shipping a regression.

**Extending the range to `0x00C0–0x024F` as well.** It works, and for `Đ` it
replaces `M`'s over-wide box with `D`'s true width. I narrowed it back to
`0x1E00–0x1EFF`: those letters already render without warnings, the improvement
is real but not observable in any assertion I could write, and changing untested
behaviour to chase an invisible gain is how the 6.11 class of bug gets made.

## What the tests pin down

Six tests, and one of them sweeps the **entire Vietnamese alphabet** — 29 base
letters plus every toned vowel, upper and lower case — asserting zero warnings.
Commenting out the extension fails three, including that sweep.

One test passes with or without the fix on purpose: `àéîõü Åžœ ĐđƠơƯư` must stay
silent, so that a future widening of the range cannot quietly break the letters
KaTeX already handles.

`renderMath` and `KATEX_OPTIONS` now live in one module, so the answer body
(through `rehype-katex`) and a citation snippet (through `MathText`) share both
the options and the metrics extension. Before this there were two copies of the
options and no shared setup to hang the extension on.

## Verify

- Ask something whose answer mixes Vietnamese with notation: no console warnings.
- `\text{}` containing Vietnamese no longer overlaps what follows it.
- The dot under `ộ` is not clipped.
