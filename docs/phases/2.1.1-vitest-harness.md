## Scope — deliberately smaller than the original §7.1 sketch

The earlier plan listed three dev dependencies. Two are not needed:

| Package | Verdict |
| --- | --- |
| `vitest` | **yes** — 4.1.11 |
| `@vitejs/plugin-react` | **no.** Only needed to compile JSX in tests. You verify the UI manually and we run no browser tests, so nothing under test renders a component. |
| `vite-tsconfig-paths` | **no.** It exists to read `paths` out of `tsconfig.json`. We have exactly one alias. A three-line `resolve.alias` does the same job with one fewer dependency, and this project's stated value is minimal dependencies. |

**One new dev dependency, pinned.**

If we ever do test a component, `@vitejs/plugin-react` gets added then, in the
phase that needs it.

## Files

**Create `vitest.config.mts`:**

```ts
import { fileURLToPath } from "node:url";
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    // Node, not jsdom: we test pure functions and route logic. UI is verified
    // by hand (see PROJECT_PLAN.md §2), so nothing here needs a DOM.
    environment: "node",
    include: ["src/**/*.test.ts"],
  },
  resolve: {
    // Mirrors the single `@/*` alias in tsconfig.json. Kept by hand rather than
    // read from tsconfig, to avoid a dependency for one line.
    alias: { "@": fileURLToPath(new URL("./src", import.meta.url)) },
  },
});
```

**Modify `package.json`:**

```json
"test": "vitest run",
"test:watch": "vitest"
```

**Create `src/lib/documents/status.ts` + `status.test.ts`** — see below.

## The "one passing test" is a real one

A placeholder `expect(1 + 1).toBe(2)` proves the runner starts but not that the
config is right — it would pass with a broken alias and an empty `include`.

Instead, the first test exercises something small and genuinely needed, through
the `@/` alias, so a misconfigured harness fails loudly:

```ts
// src/lib/documents/status.ts
import type { DocumentStatus } from "@/lib/db";

/** A document is still being worked on, so the UI should keep polling. */
export function isPending(status: DocumentStatus): boolean {
  return status === "pending" || status === "indexing";
}
```

```ts
// src/lib/documents/status.test.ts
import { describe, expect, it } from "vitest";
import { isPending } from "@/lib/documents/status";

describe("isPending", () => {
  it("is true while the document is still being indexed", () => {
    expect(isPending("pending")).toBe(true);
    expect(isPending("indexing")).toBe(true);
  });

  it("is false once indexing has settled either way", () => {
    expect(isPending("ready")).toBe(false);
    expect(isPending("failed")).toBe(false);
  });
});
```

This imports the generated database enum through the alias, so it proves the
runner starts, the alias resolves, TypeScript is understood, and our types are
reachable from tests. `isPending` is then used for real by 2.1.6's status
polling — it is not scaffolding.

## A trap I expect, and what I'll do about it

Several modules in `src/lib/` import `server-only`, which **throws by design**
when imported outside a React Server Component. Any test that reaches one will
fail with a confusing error that looks like a Vitest problem.

`status.ts` is pure and imports only a type, so 2.1.1 will not hit this. When
2.1.3 tests the repository, the fix is a one-line alias to a no-op stub:

```ts
alias: { "server-only": fileURLToPath(new URL("./src/test/server-only-stub.ts", import.meta.url)) }
```

I am flagging it now rather than adding it speculatively — YAGNI, and it is
better introduced in the phase whose failure explains why it exists.

### One deviation: the config is `.mts`, not `.ts`

As written, `vitest.config.ts` worked but warned:

```
(!) Your Vite config uses features that are unsupported by `configLoader: 'native'`:
  - ESM syntax in a file loaded as CommonJS (vitest.config.ts:1:1).
    Use a `.mjs` extension or set "type": "module" in the closest package.json
```

The same fork we took for the `scripts/*.mts` rename, and the same answer:
`"type": "module"` would change module resolution for the whole project,
including how Next reads its own configs. A `.mts` extension states the module
system for one file and touches nothing else. Renamed to `vitest.config.mts`;
warning gone, tests unchanged.

`tsconfig.json` already includes `**/*.mts`, so it stays typechecked.

### Still true from the plan

`@vitejs/plugin-react` and `vite-tsconfig-paths` were not needed. The hand-written
three-line alias resolves `@/lib/db` from the test correctly — proven by the test
passing, since a broken alias would have failed the import rather than silently
skipping.

The `server-only` trap was not hit, as predicted; `status.ts` imports only a type.
It stays flagged for 2.1.3.
