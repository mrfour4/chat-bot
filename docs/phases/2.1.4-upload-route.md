## Why the row stops at `pending`

This phase ends with a `pending` row and no Gemini call. That seam is
deliberate: it means auth, validation, dedupe and persistence can be verified on
their own, and when 2.1.5's indexing goes wrong we will know the problem is
indexing. It also costs nothing to have — `pending` is already a real state the
schema models.

---

## The guard problem

`requireTeacher()` calls `redirect()`. That is right for a page and wrong for an
API route: a `fetch` that wanted JSON would receive a 307 to `/login` and, worse,
follow it and get HTML with a 200. The caller cannot tell "forbidden" from
"here is a login page".

So `auth.ts` gains a non-redirecting sibling:

```ts
/** The signed-in teacher, or null. For routes, which must answer rather than redirect. */
export async function getTeacher(): Promise<SessionUser | null>;
```

`requireTeacher()` stays as it is for pages. Two functions because the two
callers genuinely need different behaviour, not because of duplication.

**Status codes:** guest → `401`, signed-in non-teacher → `403`. Distinguishing
them matters: 401 means "log in", 403 means "logging in will not help".

## Request and responses

`POST /api/documents`, `multipart/form-data`, field `file`.

| Case | Status | Body |
| --- | --- | --- |
| Success | `201` | the created row |
| No file field | `400` | `{ code: "no-file", message }` |
| Validation failure | `400` | `{ code, message }` from `validateUpload` |
| Duplicate checksum | `409` | `{ code: "duplicate", message, existing: { id, title } }` |
| Guest | `401` | `{ code: "unauthenticated", message }` |
| Non-teacher | `403` | `{ code: "forbidden", message }` |

`GET /api/documents` → `{ documents: DocumentRow[] }` for a teacher; this is
what 2.1.6 polls.

**Why 409 rather than silently returning the existing row:** re-uploading the
same file is usually a mistake — a teacher who thinks the first attempt failed.
Telling them it is already there, by name, is more useful than a success they
will misread. It also avoids a second index of identical bytes, which is the
expensive part.

The dedupe is on **checksum, not filename**: the same document saved under two
names is still the same document, and File Search would happily index it twice.

## One pure helper, tested

`deriveTitle(fileName)` — the teacher-facing title, from the filename:

- strips the `.pdf` extension
- turns `-` and `_` into spaces
- collapses whitespace, trims
- falls back to `"Tài liệu chưa đặt tên"` when nothing is left

Small, but it is the string every citation shows, and `tuyen-sinh-2026.pdf`
rendering as *"tuyen-sinh-2026.pdf"* in a source reference would be shabby.
Tested: normal name, underscores, no extension, unicode filename with
diacritics preserved, and a name that reduces to nothing.

The route handler itself gets no unit test — it is `cookies()`-bound and mostly
orchestration of pieces already tested. It is verified instead by (a) a real
unauthenticated `curl`, which needs no session and genuinely exercises the
guard, and (b) 2.1.6's manual upload in the browser.

### The guard, checked with a real request

```
$ curl -s -i -X POST localhost:3000/api/documents
HTTP/1.1 401 Unauthorized
content-type: application/json

{"code":"unauthenticated","message":"Vui lòng đăng nhập để tiếp tục."}

$ curl -s -i localhost:3000/api/documents
HTTP/1.1 401 Unauthorized
content-type: application/json
```

**401 with a JSON body, not a 307 to `/login`.** This is exactly what the
`getTeacher()` split was for: had the route reused `requireTeacher()`, this
request would have returned a redirect that `curl -L` — and `fetch` — would
follow to an HTML login page with a 200, leaving the client unable to tell
rejection from success. Worth one curl to know rather than assume.

The 403 branch cannot be exercised without a signed-in student session, so it
is verified in 2.4.1 alongside the RLS checks.
