# 6.6 — One refresh per change

## What you reported

> When deleting or editing a document, `GET /api/documents?page=0&pageSize=10` is
> called twice.

## Why there were two

There were two sources of truth about "something changed", and both were right:

1. The mutation's `onSuccess` invalidates the query — the request succeeded, so
   the list is stale.
2. The Realtime broadcast from 5.5 invalidates the query — the row changed in the
   database, so the list is stale.

A rename is one `UPDATE`, so both fire within a few milliseconds of each other
and React Query, seeing two invalidations of an active query, refetches twice.

Removing either one is worse than the duplicate. Drop the mutation's invalidation
and the UI depends on a websocket that may not be connected; drop the broadcast's
and another teacher's changes stop appearing.

## Coalescing instead of choosing

`useRefreshDocuments` takes both calls and schedules one invalidation on a short
timer, restarting it while calls keep arriving:

```ts
const refresh = useRefreshDocuments();   // both callers use this
```

Two signals about the same change land in the same window and produce one
request. A burst — uploading eight files, each of which broadcasts twice as it
moves `pending → indexing → ready` — collapses from sixteen refetches to a
handful, which is the case that actually mattered.

The window is 150 ms: long enough to catch a mutation and its echo, short enough
that nobody sees it. It is a coalescing window, not a debounce on user input, so
it is not `SEARCH_DEBOUNCE_MS`.

The timer is cleared on unmount, so a page left during an upload does not
invalidate a query nobody is watching.

## Verify

- Network tab, rename a document: one `GET /api/documents`.
- The same for archive, restore and delete.
- Upload several files: the table still keeps up, without a request per event.
