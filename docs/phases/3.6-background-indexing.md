# 3.6 — Upload and indexing in the background

**Goal.** The upload survives the user. Navigate away, refresh, close the tab —
indexing carries on, and the status is waiting when they come back.

---

## Why this was possible only now

D5 chose **synchronous** indexing, and the reasoning was sound at the time:
returning early and continuing in the background is not guaranteed to run on
serverless without a queue, and §5.10 kept no copy of the PDF, so the request
was the only place the bytes existed. Both halves of that have changed. 3.3
kept the bytes, and Next ships `after()`.

**D5 is reversed here**, and this doc records why.

## The shape

1. Validate, checksum, dedupe — unchanged, and still inside the request,
   because all three must be able to *reject* the upload.
2. Store the PDF. This is the step that must succeed for anything else to be
   possible, so it stays synchronous and still fails the upload closed.
3. **Return 201** with the row at `pending`.
4. `after()` runs the indexing job once the response is sent.

The client's own upload is the "uploading" state — there is no row until the
bytes land, so no database state is needed to represent it. That keeps your
four statuses without a migration:

| You asked for | Here |
| --- | --- |
| uploading | the in-flight request; no row yet |
| processing / indexing | `pending` → `indexing` |
| completed | `ready` |
| failed | `failed` |

## What makes it durable rather than merely asynchronous

`after()` alone would be a promise on a process that may not survive. Two more
things close that:

**The claim.** A worker moves a row `pending` → `indexing` with a *conditional*
update that only matches rows still `pending`, and proceeds only if it changed
a row. Two workers racing the same document — an `after()` and a sweeper — and
exactly one wins. Without this, both would upload the same PDF to Gemini and
the loser would overwrite the winner's result.

**The sweeper.** `POST /api/documents/reindex` re-drives anything left in
`pending` or `indexing` past a staleness threshold. This is only safe because
3.3 kept the bytes: the worker re-reads the PDF from storage rather than
needing the browser that uploaded it. A crash mid-index becomes a delay rather
than a document stuck forever in "Đang lập chỉ mục".

Stale means `updated_at` older than the threshold, not "not ready yet", so a
healthy in-flight index is never disturbed.

**Retry became a button.** 2.1.8 noted that since we kept no bytes, "retry" had
to mean "upload the file again". We keep them now, so a failed document
re-indexes from what is already stored.

## What is honestly still missing

If the process dies *and nobody calls the sweeper*, the row sits at `pending`
until something does. The teacher's own documents page calls it while anything
is in flight, which covers the realistic case. On a deployment, one cron entry
closes the rest — see the note in §8 of the project plan. That is the point at
which a queue would be the alternative, and it needs an account and keys the
MVP does not need yet.

## Verification

**Six checks against the hosted database, no Gemini:**

```
PASS  exactly one worker claims the document      (two claims launched together)
PASS  a later worker finds nothing to claim
PASS  a running index is not swept
PASS  a stuck index is swept
PASS  a ready document is never re-indexed
PASS  a row without a stored PDF is not swept
```

The first one is the phase's load-bearing claim, and it is a real race: two
updates issued together, exactly one matching a row.

**A finding from a failing test.** "A stuck index is swept" failed at first
because the fixture tried to backdate `updated_at` — and
`documents_touch_updated_at` rewrites it to `now()` on every update. That is
the test's problem, not the code's, and it makes the signal *stronger*:
`updated_at` cannot be forged, so it is a trustworthy liveness marker. Age is
now simulated by moving the cutoff instead of the row, which shows the same row
swept under one cutoff and left alone under another.

**Six unit tests** for `isStale`, including the boundary, a settled document
(re-driving a `ready` row would re-upload it to Gemini for nothing) and an
unparseable timestamp — which must not read as "stale forever", or every poll
would requeue the row, looking like activity while being a loop.

**Three tests against the real Gemini API** (`npm run test:api --
src/lib/documents/job.itest.ts`, ~41s, one upload):

```
PASS  indexes a document from its id alone
PASS  refuses to run twice, so two workers cannot both index it
PASS  fails a document whose stored PDF is missing, rather than hanging
```

The first is the whole phase in one assertion: a row and a stored object, with
no request and no browser, are enough. The store was checked afterwards and
left with **0 documents** — no orphans, the 2.1.5 failure mode.

Yours in the browser: upload, then immediately navigate away or refresh. Come
back and the status should be waiting for you, and eventually `Sẵn sàng`.

## A bug found while checking the data afterwards

The one document row left on the hosted project reads `ready`, but its
`gemini_document_name` points at `fileSearchStores/admissionsdocuments-6cl0if0ljufm`
— a store the **current** API key cannot see. The key was rotated; the old
store went with it.

Two consequences:

1. **The row lies.** It says `Sẵn sàng` while the assistant can retrieve
   nothing from it — §5.12's failure mode, sitting in real data.
2. **It could not be deleted.** `deleteFromStore` treated 404 as success (so a
   half-failed delete can self-heal) but let 403 throw, which the delete route
   turns into a 502. A row whose store is unreachable was therefore impossible
   to remove through the UI, forever.

`deleteFromStore` now treats 403 the same as 404, with the reasoning written
down: a 403 here means *this key can never reach that document*, so retrying
cannot succeed, and the unreachable document is unreachable either way. The
stuck row is the only part still fixable.
