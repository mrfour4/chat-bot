# 3.3 — Keep the uploaded PDF

**Goal.** Store the PDF a teacher uploads, so it can be previewed and
downloaded (3.4) — and so indexing can move off the request (3.6).

---

## Why this comes before 3.6

§5.10 discarded the bytes on purpose, and that is *precisely* why indexing has
to run inside the upload request: the file exists nowhere else, so the request
is the only place that can index it. Preview is not a neighbour of background
indexing; it is its precondition. A worker can only re-read what we kept.

## The bucket

Private, `file_size_limit` 20 MiB — the same number as `MAX_UPLOAD_BYTES`, not
a rounder one — and `allowed_mime_types` restricted to `application/pdf`. Two
gates for one rule: `validateUpload()` in the app, the bucket in the platform.

Created **in a migration**, not the Dashboard. `supabase db reset` applied it
locally, `storage.buckets` and `pg_policies` confirmed it.

## Path convention

`<uploader_id>/<document_id>.pdf`

The first segment is load-bearing. The policies read ownership out of the
**path** rather than out of storage's `owner` column, so the rule stays legible
in the policy itself and does not depend on which client performed the upload.
The document id makes a re-upload overwrite its own object instead of
accumulating a second one.

## Policies

They mirror the `documents` table policies deliberately — any teacher reads
every file, only the uploader writes or removes their own. Divergence would let
a teacher reach a PDF whose metadata row is invisible to them, or the reverse.

An **UPDATE** policy is included even though nothing "edits" a PDF: Supabase
upsert needs INSERT + SELECT + UPDATE, and re-uploading a failed document
reuses its row and therefore its path. Without the update policy that retry
fails as a policy violation — for a reason with nothing to do with the retry.

## Failing closed on a storage error

If the object cannot be stored, the upload is marked `failed` and indexing
never runs. Indexing a document we did not keep would produce one that answers
questions today and can never be re-indexed, previewed or repaired — working
and unrepairable at the same time. Better to refuse it and say so.

## Two things the database taught us

**`storage.objects` refuses direct SQL deletes.** A `protect_objects_delete`
trigger insists on the Storage API. Found by the RLS suite failing, and it
confirms `removePdf()` was right to go through the client rather than the
table. The trigger reads `storage.allow_delete_query`, so the test can clear
its own fixtures without weakening anything at runtime.

**`postgres` has `rolbypassrls`, `supabase_storage_admin` owns the table.** So
the suite can seed a fixture object, and that seeding is not itself a policy
test.

## Verification — and two flaws found in the tests themselves

`npm run test:rls` grew from 11 checks to 17. Then, as in 2.4.1, deliberately
leaky policies were added to prove the new ones fail when they should. That
exposed two flaws in the tests, not the policies:

1. **A leak reported as "0 tests run", not "1 test failed."** The two insert
   attempts shared a path, so once the leak let the first succeed, the second
   died on a duplicate key and aborted the whole `DO` block. Distinct paths
   now, and `when others` records the error instead of raising it — an
   unexpected error must fail one check, never silence all of them.
2. **The read checks passed on an empty table.** "anon cannot read stored PDFs"
   was true because there was nothing to read. Exactly the failure mode of
   §5.12: a correct refusal and an empty index look identical. The suite now
   seeds a real object first and asserts a teacher *can* see it, so the
   negatives mean something.

With the leaks re-applied: `anon cannot read stored PDFs` FAIL `[1 objects
visible]`, both insert checks FAIL `[insert was allowed]`. Leaks removed: 17
passed, 0 failed.
