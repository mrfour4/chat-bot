# 6.3 — Reindexing

## What you asked

> What exactly triggers reindexing? Whether reindexing is actually necessary for
> actions like search, edit, delete, and archive. Whether reindexing can be
> triggered only when it is genuinely required.

## What was triggering it

One effect in `use-documents.ts`:

```ts
useEffect(() => {
    if (!data.documents.some(isStale)) return;
    requestReindex().then(invalidate).catch(() => {});
}, [data]);
```

`data` is the query result *object*. Every refetch produces a new one, so the
effect re-ran after every search keystroke, rename, archive and delete. If any
row on the visible page looked stale it posted `/api/documents/reindex`, which
requeued those rows and called Gemini.

The seeded rows sit in `pending` and `indexing` with old `updated_at` values, so
`isStale` is permanently true for them. That is why it fired on essentially every
action: the condition was never going to clear on its own.

## Whether it was necessary

No. Renaming a document does not change its bytes. Archiving removes it from
retrieval, deleting removes it entirely, and searching is a `SELECT`. None of
them change what Gemini has indexed.

The sweeper exists for exactly one situation: a serverless indexing job killed
mid-flight, leaving a row stuck in `indexing` with nothing left to finish it.
That is a recovery mechanism — and a recovery mechanism should not be driven by a
client that happens to be rendering a table.

## What may call Gemini now

| Trigger | Calls Gemini | Why |
|---|---|---|
| Upload a new file | yes | there is nothing indexed yet |
| Restore an archived document | yes | it was removed from the store on archive |
| Retry on a failed row | yes | you pressed it |
| Cron `POST /api/documents/reindex` with `REINDEX_SECRET` | yes | the stuck-job sweep, on a schedule |
| Search, rename, archive, delete, paging, opening the page | **no** | nothing about the index changed |

The effect is gone. A row stuck in `indexing` still shows as such and still has
Retry in its menu, so recovery stays available — it just needs a person now.

## And no call leaves this machine

`GEMINI_BASE_URL` rewrites the host on every request, so with `npm run mock:gemini`
running, every call ends at `127.0.0.1:4010`. Your commented-out `GEMINI_API_KEY`
was the reindex failure you saw: `serverEnv()` demanded it before anything looked
at the base URL. When `GEMINI_BASE_URL` is set, the key and the store name now
fall back to placeholders, because a real key is meaningless against a mock. With
it unset nothing changes: both are still required.

So during local testing the quota is not merely unspent, it is unreachable.

## Verify

- Search, rename, archive and delete with the network tab open: no
  `/api/documents/reindex`.
- With `GEMINI_API_KEY` commented out and the mock running, upload a file: it
  indexes.
- With `GEMINI_BASE_URL` unset and no key, `/api/health` still reports the
  missing variable rather than pretending.
