## Is it worth adopting?

**For the documents panel, clearly yes.** That component currently hand-rolls
what Query does properly:

| Hand-rolled today | With Query |
| --- | --- |
| `useEffect` + `setInterval`, cleared on a `waiting` flag | `refetchInterval` returning `false` when nothing is in flight |
| `refresh()` called manually after upload and delete | `invalidateQueries` |
| `setDocuments(...)` in three places | one cache, one source of truth |
| `try/catch` around every call | `isPending` / `error` per mutation |

**For chat, no.** A conversation is append-only client state, not a cache of
server state — there is nothing to invalidate or refetch, and modelling messages
as query data would fight the library. `useMutation` for *sending* is a genuine
fit though: it gives `isPending` and `error` without hand-rolled flags, and that
is all I will use it for. The message list stays in `useState`.

Adopting a library everywhere it *can* go, rather than where it *helps*, is how
a codebase ends up harder to read than before.

## Setup, per the official guide

- `makeQueryClient()` / `getQueryClient()` — a fresh client on the server, a singleton in the browser. **Never at module scope**: on the server that would leak one user's cache into another's request.
- `staleTime: 60_000` — with server-rendered data, a zero stale time refetches everything immediately on hydration, undoing the point of rendering it on the server.
- `Providers` is a Client Component, since `QueryClientProvider` uses context.
- The documents list keeps its server-rendered first paint via `initialData`, so the page still arrives with content and RLS still scopes it.

## Outcome

**Done 2026-08-30.** `@tanstack/react-query@5.102.8`, one pinned dependency.
`npm test` 59 passed; typecheck, lint, build clean.

### What it actually removed

`documents-panel.tsx` lost a `useEffect` + `setInterval` + cleanup, a manual
`refresh()` callback, three separate `setDocuments` calls, two `try/catch`
blocks and three `useState` flags. The polling condition became one line:

```ts
refetchInterval: (query) =>
  (query.state.data ?? []).some((doc) => isPending(doc.status))
    ? POLL_INTERVAL_MS
    : false,
```

`initialData: initial` keeps the server-rendered first paint, so the list still
arrives with the HTML and RLS still scopes it. Without it the list would blank
on hydration and fill in a moment later — a regression that would have been easy
to ship unnoticed.

### Where I did not use it

The chat message list stays in `useState`. `useMutation` handles *sending* — it
gives `isPending` and `error` for free — but the conversation itself is
append-only client state with nothing to invalidate or refetch. Modelling it as
query data would fight the library.

Adopting a library everywhere it *can* go rather than where it *helps* is how a
codebase ends up harder to read than it was before.
