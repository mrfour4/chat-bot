# 3.4 — Preview and download

**Goal.** Open a stored PDF without leaving the app, and download it when
needed.

---

## The viewer

**The browser's own.** An `<iframe>` pointed at the file route. Every desktop
browser ships a competent PDF viewer with search, zoom and print already in it.

`react-pdf` / pdf.js would have been ~1 MB of JavaScript plus Turbopack worker
configuration to rebuild something the platform provides — and it would have
had to be loaded before a teacher could look at a page of their own file.

**The honest caveat:** iOS Safari and some Android browsers refuse to render a
PDF inside an iframe, and there is no reliable way to detect that before it
fails. So **"Mở trong tab mới" is always visible**, not offered as an error
path. The failure mode is a working link, not a blank rectangle.

## Inline, not a dialog

The preview expands under its row, for the same reason 2.1.7 made the delete
confirmation inline: the teacher's eyes stay on the row they are acting on. It
also avoids a dialog's focus trap, escape handling and scroll locking for what
is really just a longer row — and avoids installing a `dialog` component.

## The route

`GET /api/documents/[id]/file` → teacher check → row read **through the user's
client** so RLS decides → 302 to a signed URL.

**A redirect, not a stream.** Proxying up to 20 MB through the route would pull
the whole file into this process's memory to no purpose when storage can serve
it directly.

**Sixty seconds.** The signed URL is a bearer token in a query string; it will
end up in history and in logs. Long enough to open the viewer, far too short to
be worth passing on. `cache-control: no-store` on the redirect, because the
thing it points at is dead in a minute.

**`?download=1`** asks storage for `Content-Disposition: attachment` under the
original filename. Without it the browser renders inline, which is what the
preview wants — one route, two dispositions, no second endpoint.

**Rows from before 3.3** have no object, and get a 404 that *says the file was
never kept* and what to do about it. "Never stored" and "broken" must not read
the same. Their title is plain text rather than a control that would do nothing.

## Verification

Ten checks against the **hosted** project — the one the app actually runs on —
with no Gemini involved:

```
PASS  teacher can store a PDF
PASS  re-upload overwrites its own object      (the 3.3 upsert path)
PASS  cannot write into another user's folder
PASS  bucket refuses non-PDF
PASS  signed URL serves the PDF                (%PDF- magic bytes back)
PASS  served inline as application/pdf
PASS  download option sets attachment
PASS  anonymous fetch is refused
PASS  expired signed URL is refused            (waited it out)
PASS  teacher can remove their own object
```

The script was throwaway and is not committed: it needed a real password, and
the durable version of these checks is `npm run test:rls`, which proves the same
policies without credentials.

The migration was pushed to hosted with `supabase db push` — the app points at
the hosted project, so a local-only bucket would have made every preview 404.

Yours in the browser: click a document title, check the PDF renders, download
it, and confirm the old row without a file explains itself.
