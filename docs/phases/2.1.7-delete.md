## The ordering question, and why it has a right answer

Deleting means two things: the Gemini document, and the Postgres row. They can
fail independently, so the order decides what a half-failure leaves behind.

**Row first, then Gemini** — if the second call fails, the store keeps a
document that nothing points at. No row, no `gemini_document_name`, no way to
reach it from the UI. It consumes quota forever and **nothing can ever clean it
up**.

**Gemini first, then the row** — if the second call fails, the row survives,
still visible, still deletable. Pressing delete again finds the Gemini document
already gone, treats that as success, and removes the row.

**So: Gemini first.** The failure mode is self-healing rather than permanent,
which is the whole argument. It depends on one detail:

> **A Gemini `404` counts as success.** The goal state — that document not
> being in the store — is already true. Treating "already gone" as an error is
> what would break the retry.

Two facts from earlier phases apply directly:

- `documents.delete` needs `config: { force: true }`, or it fails `400 FAILED_PRECONDITION — Cannot delete non-empty Document` (2.1.0). Every real document is non-empty, so without this it fails **every time**.
- A `failed` row may have no `gemini_document_name` at all — 2.1.5 discards the uploaded document on failure. That is not an error; there is simply nothing to delete, and we go straight to the row.

## Route

`DELETE /api/documents/[id]` — teacher only, 401/403 as in 2.1.4.

| Case | Result |
| --- | --- |
| Success | `200 { ok: true }` |
| Not found, or not the caller's | `404` — RLS returns no row either way, and saying which would leak that a document exists |
| Gemini delete fails | `502`, row kept, message says to try again |

Authorization is RLS, not the route: `documents_delete_own_teacher` means a
teacher can only delete their own. The route reads the row through the user's
client first, so a document belonging to another teacher is simply not there.

## UI: inline confirmation, not a dialog

Delete is destructive and unrecoverable — the PDF is not stored (§5.10), so the
teacher would have to find the original file again.

The row expands into a confirmation in place:

```
dean moi 1                          Sẵn sàng    [Xoá]
                    ↓
dean moi 1        Xoá tài liệu này? [Xoá]  [Huỷ]
```

**Not `window.confirm`** — it blocks the page, cannot be styled, and browsers
let users suppress it permanently, which would silently turn a destructive
action into a one-click one.

**Not a modal dialog either.** shadcn's `AlertDialog` is not installed, and
adding it would pull a portal-based component into a page built with plain
brand-token markup — the same mismatch I avoided in 2.1.6. An inline confirm
keeps the teacher's eyes on the row they are about to remove, which matters
more here than in a modal that names it in prose.
