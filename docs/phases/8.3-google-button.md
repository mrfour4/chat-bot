# 8.3 — The button

## Where it sits

Inside the existing card, above the email fields, with a divider between:

```
┌─────────────────────────────┐
│  [G]  Tiếp tục với Google   │
│  ───────── hoặc ─────────   │
│  Email                      │
│  Mật khẩu                   │
│  [      Đăng nhập      ]    │
└─────────────────────────────┘
```

On both the sign-in and the sign-up view, because someone arriving at "create an
account" is exactly who wants the one-click option.

Google above the password fields rather than below, because it is the shorter
path and burying it under a form people do not need to fill in wastes it.

## The slot, rather than a flag

`SignInForm` and `SignUpForm` take `oauth?: ReactNode`. The login page — a
server component — decides whether to pass one:

```tsx
const oauth = googleAuthEnabled() ? <GoogleButton /> : undefined;
```

The alternative was `<SignInForm googleEnabled />`, which would have put the
decision inside a client component and needed the flag exposed as
`NEXT_PUBLIC_…`. A slot keeps the whole question on the server, and the forms
never learn that Google exists. The divider is part of the slot's rendering, so
turning Google off cannot leave a stray "hoặc" line behind — there is a test for
that specifically, since it is the obvious way to get this wrong.

## Why the button hides itself

`googleAuthEnabled()` is simply whether `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID`
is set. The provider's `enabled = true` in `config.toml` is a literal boolean —
`env()` substitution only works on strings — so the provider cannot be
env-gated. Without a gate on the *button*, a fresh clone with no Google
credentials would show an inviting button that fails at Google with an
unexplained error.

Verified at runtime in both directions, not just unit-tested, because the page's
ternary is the one link a unit test does not reach:

```console
$ # client id commented out in .env.local, dev restarted
google_marks with NO client id: 0
password form still there: 1
$ # client id restored, dev restarted
google_marks restored: 1
```

## Details worth naming

**The Google mark is an inline SVG**, not a lucide icon — lucide ships no brand
logos, and Google's branding terms require the official four-colour mark. It
carries `data-icon="inline-start"` and no size class, so `Button`'s own CSS
sizes it; hardcoding `size-4` would have overridden the button's sizing rules
and broken if the button size ever changes.

**The pending state matches `AuthSubmit`** — the mark is replaced by a `Spinner`
and the label by `common.processing`. The redirect to Google takes a moment, and
a button that looks inert invites a second click. `useTransition` rather than
local state so the pending flag covers the server action *and* the redirect.

**Errors reach the user twice over.** A failure to even start the flow (no
provider configured, no usable origin) returns from the action and becomes a
toast. A failure after Google redirects back comes through `/login?error=…` as
an alert on the page (8.2). Different moments, different mechanisms — the toast
would be lost across a full page navigation.

**No `next` is passed yet.** `GoogleButton` accepts one, and `safeNextPath`
validates it, but the login page has no notion of "where you were heading"
today — the middleware redirects to `/login` without recording an origin. The
parameter exists so that when it does, this side needs no change.

## Tests

`src/components/auth/sign-in-form.test.tsx` renders both forms through
`NextIntlClientProvider` and asserts the slot appears above the email field and
that the divider disappears with it. Falsified by making the divider
unconditional: 1 of 2 fails.

`src/lib/env.test.ts` covers the gate itself, both ways.

Full run: **181 tests across 31 files**, plus typecheck, lint, build and
`format:check` clean, and `29 passed, 0 failed` on the RLS suite.
