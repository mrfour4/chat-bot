# 2.2.1 · The ungrounded guard

**Type:** pure logic, test-first · **the most important behaviour in the product**
**Estimated:** ~30 minutes · **API calls: 0**
**Depends on:** 2.1 · **Blocks:** 2.2.3, 2.3.1

---

## What this is

§5.7 layer 3. Tooling and a system instruction both *ask* the model to answer
only from the documents. Neither *guarantees* it. This does:

> If the response carries no grounding, the model's text is discarded and the
> refusal is returned instead — whatever the text said.

That inversion is the whole point. We do not inspect the answer for signs of
hallucination, which is unreliable and unfalsifiable. We check for **evidence
that retrieval happened**, and treat its absence as disqualifying. An answer
without a source is not an answer, however plausible it reads.

Two earlier findings make this urgent rather than theoretical:

- In 2.1.5, a query returned **zero grounding chunks moments after the same filter had worked** — most likely the model answering without running the retrieval tool under quota pressure. If that happens in production, this guard is the only thing between a student and a confident fabrication.
- Also in 2.1.5, an unscoped question over two documents produced an answer that presented one university's data while referring to "hai trường khác nhau". Grounding metadata is what lets us tell which document an answer actually came from.

## Interface

```ts
// src/lib/rag/grounding.ts
export const REFUSAL: string;   // Vietnamese

export type GroundingCheck = {
  grounded: boolean;
  answer: string;               // the model's text, or REFUSAL
  reason: "ok" | "no-metadata" | "no-chunks" | "empty-text";
};

export function enforceGrounding(input: {
  text: string | undefined;
  groundingMetadata: GroundingMetadata | undefined;
}): GroundingCheck;
```

`reason` exists so failures are diagnosable in logs and assertable in tests —
"the answer was refused" and "the answer was refused *because retrieval never
ran*" are very different operational facts.

**Fails closed.** Every unexpected shape — undefined metadata, empty chunk
array, missing text — returns the refusal. There is no input for which this
returns ungrounded model text.

## Tests, written first

1. grounded response with chunks → the model's text is returned, `reason: "ok"`
2. **`groundingMetadata` undefined → refusal, and the model's text does not appear in the output**
3. `groundingChunks` empty array → refusal
4. `groundingChunks` undefined but metadata present → refusal
5. grounded, but the model returned empty text → refusal, not an empty bubble
6. **the refusal is returned verbatim, never blended with the model's text**
7. the refusal is Vietnamese
8. a long confident hallucination with no grounding → still refused (the headline case, written as a scenario so the intent survives refactoring)

Test 2 and test 8 are the ones that matter. Both assert on the *absence* of the
model's words, not merely on a flag.

## Outcome

**Done 2026-08-30.** Tests written first and observed failing, then the
implementation. `npm test` 40 passed; typecheck and lint clean. Zero API calls.

Eight tests. The two that carry the weight assert on the **absence of the
model's words**, not on a boolean:

```ts
expect(result.answer).not.toContain("55 triệu");
expect(result.answer).not.toContain("27,5");
expect(result.answer).toBe(REFUSAL);
```

A test asserting only `grounded === false` would pass even if we returned the
hallucination alongside the flag. These fail unless the text is genuinely gone.

`reason` distinguishes `no-metadata` from `no-chunks`: the first means retrieval
never ran, the second that it ran and found nothing. Same refusal to the
student, very different operational fact for us — and 2.1.5 showed the first
can happen under quota pressure.
