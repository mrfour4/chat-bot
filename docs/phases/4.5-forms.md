# 4.5 — Forms with TanStack Form and Zod

**Goal.** Every form validated by a schema, laid out with `Field`, with no more
hand-rolled `label` + `input` + `span` scaffolding.

---

## No official skill exists for TanStack Form either

Checked the same way as Query in 2.3.5, rather than assumed: `@tanstack/intent
list` finds only `dotenv`, and the only `skills/` directory under
`@tanstack/` belongs to `devtools-event-client` — devtools, not forms. The API
was read out of `node_modules/@tanstack/react-form/dist/esm/*.d.ts` instead.

**Zod needs no adapter.** TanStack Form v1 validates against **Standard
Schema**, which Zod 4 implements, so `validators: { onChange: signInSchema }`
works with the schema itself. No `zodValidator` wrapper, no extra dependency.

## The schemas are shared, not duplicated

`src/lib/validation/` holds `auth.ts`, `chat.ts` and `upload.ts`, imported by
**both** the form and the server:

- `signInSchema` / `signUpSchema` — the form validates as you type; the server
  action re-parses. A client-side rule the server does not also enforce is
  decoration.
- `MAX_QUESTION_LENGTH` — the composer and `/api/chat` now import one constant.
  It was declared separately in the route before; had they drifted, the box
  would have cheerfully sent what the route rejects.
- `MAX_UPLOAD_BYTES` — the browser checks size before spending a request. The
  `%PDF-` signature check stays server-side, because `File.type` comes from the
  extension and a renamed executable arrives claiming to be a PDF.

## The sign-in and sign-up forms became two components

They were one component with `isSignUp` threaded through six places. The type
checker made the real objection: **one form cannot have two shapes.**
`defaultValues` for sign-up carries `fullName`, sign-in's schema does not — so
the shared component could not be typed without weakening one of the schemas.

Two components, one `AuthField`, `AuthResult` and `AuthSubmit` between them. No
ternaries left.

The server actions changed signature from `(prevState, formData)` to a typed
input object, since `useActionState` is gone. They validate with the same schema
before touching Supabase.

## Field states

`data-invalid` on the `Field` and `aria-invalid` on the control, both from one
`invalid` expression — the visible state and what a screen reader is told cannot
disagree.

The composer uses `isDirty` rather than `isTouched`: an empty question box on
arrival is not a mistake to report, but one that had text and was emptied is.

## Verification

15 new tests, 88 total. The ones worth naming:

- **sign-in does not impose the password minimum.** A user whose password
  predates the rule must still be able to sign in; enforcing it there would lock
  them out of their own account for a rule they never agreed to.
- **the upload boundary is inclusive** — exactly `MAX_UPLOAD_BYTES` is accepted,
  one byte more is not.
- **the question limit is the route's own constant**, so a drift between them
  fails a test rather than a user's question.
