# 9.5 — Forgot password

Two pages: `/forgot-password` asks for an address, and `/profile/password` is
where the emailed link lands. `/auth/confirm` already existed and needed no new
branch — it calls `verifyOtp`, which is exactly what a recovery token wants.

## The finding: the default email cannot work with a server-rendered app

This is the part worth reading. The default recovery template links to Supabase's
own `/auth/v1/verify`, which redirects back like this — captured by following a
real generated link:

```
303 -> http://localhost:3000/auth/confirm?next=/profile/password#access_token=eyJhbGciOi…&type=recovery
```

The session arrives in the **URL fragment**. A fragment is never sent to the
server, so `/auth/confirm` sees no `token_hash` and no `type`, and answers
`/login?error=confirm`. The flow would have failed for every user, and it would
have looked like a bug in our route.

`supabase/templates/recovery.html` uses `{{ .TokenHash }}` instead, putting the
credential in the query string where a server can read it:

```
http://localhost:3000/auth/confirm?token_hash=…&type=recovery&next=/profile/password
```

The template is Vietnamese, says which address asked, and states that ignoring
the email leaves the current password untouched — the thing a person actually
wants to know when an unexpected reset email arrives.

## The finding before that: the allow-list silently ignored our destination

The first probe produced an email pointing at `http://127.0.0.1:3000` — the
`site_url` fallback — not the `/auth/confirm?next=/profile/password` the action
asked for. Supabase validates `redirectTo` against `site_url` plus
`additional_redirect_urls`, and an entry of `.../auth/callback` does not match a
URL carrying `?next=…`. It does not complain; it substitutes.

Hence the wildcard:

```toml
additional_redirect_urls = [
  "http://localhost:3000/**",
  "http://127.0.0.1:3000/**",
]
```

Still pinned to scheme, host and port — it only opens paths on an origin we
already control, which is the boundary the list exists to draw. A silent
substitution is the worst failure mode available here, so this is worth the
breadth.

## Verified end to end

The token is issued by whichever Supabase the request reached, so the dev server
was pointed at the local stack for one run (and put back afterwards):

```console
recover=200
clicking: http://localhost:3000/auth/confirm?token_hash=b84d28ca…
step 1: 307 -> http://localhost:3000/profile/password
session cookie set: 1
step 2: /profile/password -> 200, renders type="password"
```

A real email, read out of Mailpit, clicked as a browser would, arriving
authenticated on the set-password page.

## Two other things this phase fixed

**An open redirect in `/auth/confirm`.** It read `searchParams.get("next") ?? "/"`
and redirected there unchecked — pre-existing since Phase 1, and now reachable
from an emailed link, which is precisely the context where a crafted `next`
matters. It uses `safeNextPath` (8.2), like the OAuth callback.

**No account-existence oracle.** `sendPasswordReset` returns the same message
whether or not the address has an account. Confirming which addresses are
registered is a small leak that costs nothing to avoid.

## Not verified here

The template and the wildcard allow-list are local until `config push` sends them
to hosted, which 9.6 does in one deliberate push. Until then a recovery email
from the hosted project still uses the default template. Note also that hosted's
built-in SMTP allows **2 emails per hour**.

## A fixture that breaks GoTrue

Worth knowing, because it will happen again. Requesting recovery for
`student@example.com` returned 500:

```
error finding user: Scan error on column "confirmation_token": converting NULL to string is unsupported
```

Rows inserted into `auth.users` by direct SQL — the RLS fixtures, the Google
probe in check 29 — leave token columns `NULL` where GoTrue expects `''`. Such a
user works for RLS checks but cannot take part in an email flow. Use the signup
API when a test needs a real account.
