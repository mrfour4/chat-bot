# 8.2 — The OAuth flow

The exchange itself: starting the flow, handling the return, and deciding where
the user lands.

## Why this could not be a branch in `/auth/confirm`

That route calls `verifyOtp` with a `token_hash`. OAuth returns a `code` to be
traded via `exchangeCodeForSession`. Different credential, different call, and
different failure modes — a branch would have shared nothing but the redirect at
the end. So `/auth/callback` is its own route.

## Where the flow starts, and why on the server

`signInWithGoogle` is a server action, next to the existing `signIn` and
`signUp`. The reason is the PKCE code verifier: it is generated when the flow
starts and must still be readable when the callback runs.

`@supabase/ssr`'s server storage adapter (`dist/main/cookies.js`) contains:

```js
// We don't have an `onAuthStateChange` event that can let us know that
// the PKCE code verifier is being set. Therefore, if we see it being
// set, we need to apply the storage (call `setAll` so the cookie is
// set properly).
if (key.endsWith("-code-verifier")) {
```

So a server action's write is flushed immediately, and the verifier lands in an
`HttpOnly` cookie. Starting from the browser client would have worked too, but
the verifier would sit in a cookie readable by any script on the page. Same
number of lines, strictly less exposure — an easy choice, but only visible by
reading the adapter.

The action uses `skipBrowserRedirect: true` and then Next's own `redirect()`.
`signInWithOAuth` would otherwise try `window.location.assign`, which does not
exist on the server; it returns the URL either way.

## The callback does not pass a flow id, deliberately

`auth-js` 2.112.4 supports several PKCE flows at once, keying each verifier as
`<storageKey>-flow-<flowId>-code-verifier`, and the callback can name one:

```js
const flowId = requestUrl.searchParams.get('sb_flow_id')
supabase.auth.exchangeCodeForSession(code, flowId ? { flowId } : undefined)
```

That parameter only appears when `experimental.appendPkceFlowIdToRedirects` is
enabled, and `@supabase/ssr` does not enable it. So `sb_flow_id` never arrives,
and we call `exchangeCodeForSession(code)` with no options — which reads the
fixed legacy key that `storePKCEVerifier` writes for every flow.

Guessing or fabricating a flow id would be worse than omitting it. From the
SDK's own comment:

> deliberately no fallback to the fixed legacy key: submitting another flow's
> verifier would burn the single-use auth code

## Three ways the callback can fail, three different answers

| Arrives as | Meaning | Result |
|---|---|---|
| `?error=access_denied` | user pressed Cancel at Google | `/login?error=oauth_cancelled` |
| `?error=…` anything else | provider or config problem | `/login?error=oauth` |
| no `code`, or the exchange fails | stale link, replayed code, clock skew | `/login?error=oauth` |

Cancelling is not an error, and telling someone "sign-in failed" when they
chose to back out is a small lie the UI does not need to tell.

Verified against the running server:

```console
$ curl -sw '%{http_code} %{redirect_url}' localhost:3000/auth/callback
307 http://localhost:3000/login?error=oauth
$ curl -sw '%{http_code} %{redirect_url}' 'localhost:3000/auth/callback?error=access_denied'
307 http://localhost:3000/login?error=oauth_cancelled
$ curl -sw '%{http_code} %{redirect_url}' 'localhost:3000/auth/callback?code=not-a-real-code'
307 http://localhost:3000/login?error=oauth
```

## The login page was swallowing errors already

`/auth/confirm` has redirected to `/login?error=confirm` since Phase 1, and the
login page never read `error` — so an expired confirmation link produced a
silent, unexplained login page. Fixed here because OAuth needed the same
plumbing.

`loginErrorKey` maps the query value to a catalogue key and returns `null` for
anything unrecognised, so a crafted `?error=` cannot choose arbitrary copy.
`Object.hasOwn` rather than `value in KEYS` or `KEYS[value]`, because
`?error=toString` would otherwise resolve through the prototype chain — there is
a test for exactly that, and for `__proto__` and `constructor`.

Counting rendered alerts rather than searching the HTML for the message text,
because Next serialises the whole message catalogue into the RSC payload — the
first version of this check "passed" for an unknown error value simply by
finding the Vietnamese string in that payload:

```console
error=oauth            alert_elements=1
error=oauth_cancelled  alert_elements=1
error=confirm          alert_elements=1
error=bogus            alert_elements=0
error=__proto__        alert_elements=0
```

## Nothing is hardcoded to localhost

You said you will deploy to Vercel later, so the callback URL is derived per
request instead of written down:

`resolveOrigin` takes the configured `NEXT_PUBLIC_SITE_URL` if there is one,
then `x-forwarded-host` / `x-forwarded-proto` (which is what Vercel sets), then
`host`. For a bare host it assumes `http` for loopback and `https` for anything
else, because a real domain served over plain HTTP is not a case worth
supporting.

It refuses a host containing anything but a host and port. A `Host` header is
client-supplied, and `https://example.com/path@evil.com` style values are how
that becomes an open redirect. Chained proxy values (`a.example, b.example`)
take the first entry.

`safeNextPath` guards the other direction — where the user lands *after*
sign-in. It accepts only a plain path on this origin, rejecting absolute URLs,
protocol-relative `//host`, backslashes (which some clients normalise to `/`),
and control characters or spaces.

## Compared with the official guide

<https://supabase.com/docs/guides/auth/social-login/auth-google> — same
approach, and it confirms the server-side shape. Three places this
implementation is deliberately different:

**The `next` guard.** The guide's callback:

```ts
let next = searchParams.get('next') ?? '/'
if (!next.startsWith('/')) {
  next = '/'
}
```

`startsWith("/")` alone accepts `//evil.example.com`, which browsers treat as
protocol-relative and send off-origin, and `/\evil.example.com`, which some
clients normalise the same way. `safeNextPath` rejects both, plus control
characters. Its test file lists every case.

**The origin.** The guide branches inline on `NODE_ENV` and `x-forwarded-host`.
`resolveOrigin` does the same job as a pure function with tests, and validates
the host — a `Host` header is client-supplied.

**Where a failure lands.** The guide redirects to a dedicated
`/auth/auth-code-error` page. We reuse `/login?error=…`, which already exists
and can explain itself in Vietnamese, and which distinguishes cancelling from
failing.

## Open item: linking a Google identity to an existing email account

The official guide does not cover it, so this stays an observation rather than a
claim. `auth.identities` holds one row per provider per user, so a linked
account shows two rows sharing a `user_id`. Locally,
`GOTRUE_SECURITY_MANUAL_LINKING_ENABLED=false` — that only disables the manual
linking API; automatic linking on a verified email is separate and internal to
GoTrue.

After your first Google sign-in with an address that already has a password
account, this answers it:

```bash
docker exec -i supabase_db_admissions-advisor psql -U postgres -d postgres -c \
  "select u.email, i.provider, i.created_at
     from auth.identities i join auth.users u on u.id = i.user_id
     order by u.email, i.created_at;"
```

Two rows with one `user_id` means linked; two different `user_id`s means two
separate accounts, and the profile row for each is separate too.
