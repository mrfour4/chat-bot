# 8.1 — The Google provider

## What you asked for

> i want support login with google

Plus, mid-phase:

> in current i want test in local, and in the feature i will deploy this app to vercel

So: make it work locally now, and do not bake `localhost` into anything that
will later run on Vercel.

## What changed

`supabase/config.toml` — a `[auth.external.google]` block, and a fix to
`additional_redirect_urls` that was needed regardless of Google.

`.env.example` — the two variables, with a note on which one is secret.

No migration. See "The profile trigger already handles Google" below.

## The redirect allow-list was broken before Google

It read:

```toml
additional_redirect_urls = ["https://127.0.0.1:3000"]
```

Two problems. The scheme is `https`, but the dev server serves `http`. And
there is no path, while the comment directly above the setting says the list
holds *exact* URLs. Supabase validates the `redirectTo` we ask for against
`site_url` plus this list, so no OAuth callback could ever have matched it.

It now lists the exact callback on both hosts:

```toml
additional_redirect_urls = [
  "http://localhost:3000/auth/callback",
  "http://127.0.0.1:3000/auth/callback",
]
```

Both, because `site_url` says `127.0.0.1` while `next dev` serves `localhost`,
and browsers treat those as different origins. Whichever you type in the
address bar, the callback resolves.

## Three things verified rather than assumed

**1. The Supabase CLI reads `.env.local`.** This is the one that saves you a
file. `env()` substitution in `config.toml` is documented as reading "the
environment", and it was not obvious whether that included the same
`.env.local` Next.js uses. Probed by putting a placeholder in `.env.local`,
restarting, and reading the container's environment:

```console
$ docker exec supabase_auth_admissions-advisor env | grep GOOGLE
GOTRUE_EXTERNAL_GOOGLE_ENABLED=true
GOTRUE_EXTERNAL_GOOGLE_CLIENT_ID=probe-placeholder.apps.googleusercontent.com
GOTRUE_EXTERNAL_GOOGLE_REDIRECT_URI=http://127.0.0.1:54421/auth/v1/callback
```

One file, two consumers. The CLI substitutes it into `config.toml`; Next reads
it to decide whether to show the button (8.3).

**2. The provider is wired, before any UI exists.** A placeholder client id is
enough to prove this, because the redirect is built by Supabase and only
*rejected* later by Google:

```console
$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}" \
    "http://127.0.0.1:54421/auth/v1/authorize?provider=google"
302 https://accounts.google.com/o/oauth2/v2/auth?client_id=probe-placeholder…&scope=email+profile
```

**3. The callback URI Google needs is derived, not something you choose.** Note
the third line of the probe above: `GOTRUE_EXTERNAL_GOOGLE_REDIRECT_URI` is
`http://127.0.0.1:54421/auth/v1/callback` — port **54421**, the Supabase API
port, and Supabase's own path. It is emitted even though `redirect_uri = ""` in
config.toml. This is the value Google Cloud Console wants, and it is the step
most walkthroughs get wrong by pasting the app's own URL (`:3000`) instead.

There are two different "callbacks" in this flow, which is why it is easy to
confuse them:

| URL | Belongs to | Who needs to know it |
|---|---|---|
| `http://127.0.0.1:54421/auth/v1/callback` | Supabase Auth | **Google Cloud Console** |
| `http://localhost:3000/auth/callback` | this app (8.2) | `additional_redirect_urls` |

Google returns the user to Supabase; Supabase then returns them to us.

## What was deliberately not enabled

`skip_nonce_check` stays `false`. The provider-list comment in `config.toml`
says it is "Required for local sign in with Google auth", which reads like a
requirement for what we are doing — it is not. It applies to the ID-token flow
(`signInWithIdToken`, used by Google One Tap and native SDKs), where the client
supplies a nonce. We use the authorization-code redirect flow, which has no
nonce, so enabling it would weaken the config — and `config push` would carry
that weakening to the hosted project — in exchange for nothing.

If sign-in ever fails with a nonce error, that is the setting to revisit.

`email_optional` also stays `false`: `public.profiles.email` is `NOT NULL`, so
a Google account with no email address must fail loudly rather than half-create
a user.

## The profile trigger already handles Google

`handle_new_user` (in `20260830061744_init.sql`) reads:

```sql
nullif(new.raw_user_meta_data ->> 'full_name', '')
```

`full_name` is exactly what Supabase writes into `user_metadata` for a Google
identity — the `auth-js` docblock for `exchangeCodeForSession` shows it in its
own example response, alongside `name`, `email_verified` and `sub`. So no
migration. This is confirmed against your real database in 8.2, after the first
real sign-in, rather than taken on trust from a comment.

# Google Cloud Console — the setup walkthrough

Fifteen minutes, once. You need a Google account; you do not need billing.

## 1. Create (or pick) a project

<https://console.cloud.google.com/projectcreate>

Name it something you will recognise later — `admissions-advisor` — and create
it. If you already have a project you use for this app, select it from the
picker in the top bar instead.

## 2. Configure the consent screen

<https://console.cloud.google.com/auth/overview>

Google will not issue credentials until this exists.

- **Audience: External.** "Internal" is only available to Google Workspace
  organisations and would restrict sign-in to your own domain.
- **App name** — what students will see on the Google consent page. Use the
  real name: `Tư vấn tuyển sinh` (or the English name, your call).
- **User support email** — your own address.
- **Developer contact information** — your own address again.
- **Scopes: change nothing.** Supabase requests `email profile` (visible in the
  probe above). Both are non-sensitive, so there is no Google review and no
  verification wait.

While the app is in **Testing** status, only accounts you list as test users can
sign in. Add `tu.le@devsamurai.com` — and any other account you want to test
with — under **Audience → Test users**. This is the single most common reason a
first Google sign-in fails with `access_denied`.

## 3. Create the OAuth client

<https://console.cloud.google.com/apis/credentials>

**Create credentials → OAuth client ID**

- **Application type: Web application.**
- **Name** — internal label only; `admissions-advisor local` is fine.
- **Authorised JavaScript origins** — leave empty. The redirect flow never
  calls Google from the browser's JS context.
- **Authorised redirect URIs** — add exactly this, for local development:

  ```
  http://127.0.0.1:54421/auth/v1/callback
  ```

  Google accepts `http` and a private IP here only for loopback addresses,
  which is why this works without HTTPS. **Do not** add `localhost:3000` or
  `127.0.0.1:3000` — those are this app's own callback, and Google never talks
  to them.

Press **Create**. Google shows a client ID and a client secret. The secret is
shown once; copy both now.

## 4. Put them in `.env.local`

Replace the two placeholder values 8.1 left there:

```dotenv
SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID=<the client id>.apps.googleusercontent.com
SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET=<the client secret>
```

`.gitignore` excludes `.env*`, so neither is committed. The client id is public
by design — it appears in the redirect URL — but the secret is not.

## 5. Restart both processes

The local stack reads `config.toml` and the environment **only at start**, and
`next dev` reads `.env.local` only at boot. A hot reload is not enough:

```bash
supabase stop --project-id admissions-advisor   # your data is preserved
supabase start
npm run dev
```

Never `supabase stop --all`: this machine runs company infrastructure in other
Docker containers.

Confirm the real client id took effect:

```bash
docker exec supabase_auth_admissions-advisor env | grep CLIENT_ID
```

## When you deploy to Vercel

Nothing here is localhost-specific except the URLs, and none of them are baked
into the app (8.2 derives the callback from the incoming request). At deploy
time:

1. **Google Cloud Console → your OAuth client → Authorised redirect URIs**: add
   the hosted Supabase callback, which uses your project ref rather than the
   local port:

   ```
   https://qllblmgyqlzgzdczvqds.supabase.co/auth/v1/callback
   ```

   Keep the loopback one; a client may hold several.

2. **`supabase/config.toml`**: add your Vercel URL to `additional_redirect_urls`
   and set `site_url` to it. A preview-deployment wildcard
   (`https://<project>-*.vercel.app/auth/callback`) is supported if you want
   Google sign-in on previews.

3. **Push the config** — this is the step to run deliberately, because
   `config push` sends the *whole* file, not just the Google block:

   ```bash
   supabase config push --project-ref qllblmgyqlzgzdczvqds
   ```

   Read the diff it prints. Any auth setting changed in the Dashboard by hand
   will be overwritten by what is in this file.

4. **Vercel environment variables**: set both `SUPABASE_AUTH_EXTERNAL_GOOGLE_*`
   values. The secret is not used by the app itself, but the client id is — it
   is what makes the button appear (8.3).

Deliberately **not** done now: the hosted project is untouched, and Google is
enabled locally only. Pushing today would switch on a provider holding
placeholder credentials.
