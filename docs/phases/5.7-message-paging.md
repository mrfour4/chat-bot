# 5.7 — Message paging and the scroller

**Goal.** A long conversation opens quickly, scrolls smoothly, and loads its
older messages when you scroll up towards them.

---

## 1. shadcn's MessageScroller does all three things you asked for

You pointed at it and asked whether it could be integrated. It can, and reading
it changed the plan: **chat does not need TanStack Virtual.**

From the registry source and `@shadcn/react@0.3.0`'s type definitions — the docs
page for it does not exist:

- Every `MessageScrollerItem` carries **`content-visibility: auto`** with
  `contain-intrinsic-size`. The browser skips rendering off-screen rows without
  unmounting them: virtualization with none of the usual costs — Ctrl-F still
  finds text, there is no measurement cache to invalidate, and nothing is
  absolutely positioned.
- `MessageScrollerViewport` takes **`preserveScrollOnPrepend`** — the thing that
  makes "load older" not throw the reader across the page.
- `useMessageScrollerScrollable()` reports `{ start, end }`, which is how the
  list knows it is near the top.

TanStack Virtual would have replaced all of that with a measurement cache, an
absolutely-positioned inner container, and a scroll-anchoring problem to solve
by hand. It stays out of the chat. (5.8 is a different question: a history list
is uniform rows and has no scroller written for it.)

## 2. Cursor pagination, keyed on more than a timestamp

```
GET /api/conversations/{id}/messages?before=<created_at>,<id>&limit=25
```

Newest-first from the server, reversed for display, 25 to a page as you asked.

**The cursor is `(created_at, id)`, not `created_at`.** Every turn writes the
question and the answer in the same round trip, so two messages sharing a
timestamp to the millisecond is the normal case, not an edge case. A cursor on
the timestamp alone would either skip one of them or repeat it forever,
depending on which side of the comparison it fell.

```sql
(created_at, id) < (:cursor_created_at, :cursor_id)
```

PostgREST has no row-value comparison, so this is expressed as
`created_at < c OR (created_at = c AND id < i)` — the same predicate, spelled
out.

## 3. Paging lives in the message array, not beside it

`useChat` already owns the message list, because asking a question appends to
it. Older pages **prepend to that same array** rather than arriving from a
second source.

The alternative — `useInfiniteQuery` for history plus local state for the live
turn — means two lists that have to agree about order, about the message the
server has just persisted, and about what happens when a page boundary lands
mid-turn. One array has none of those questions.

The trade is that pages are not cached: reopening a conversation re-reads the
newest 25. For a page that is nearly always entered fresh, that is the cheaper
mistake.

## 4. The message the server has not sent yet

A live answer is added to the array with a client-side id, while the same
message exists in the database with a different one. That is fine going
forward, and it would break paging backwards: a cursor built from the last
message would use an id the server has never seen.

So the cursor is taken from the **oldest message that came from the server**,
tracked as its own value rather than derived from the array. Locally-created
messages are never older than the loaded page, so they can never be the cursor.

## 5. Scrolling

`MessageScrollerProvider` with `autoScroll` and `defaultScrollPosition="end"`
replaces the `endRef` + `scrollIntoView` effect, which was also where
`prefers-reduced-motion` had to be honoured by hand (2.5). The scroller does it.

`scrollAnchor` marks the user's own message as the row to hold in view when the
answer arrives, so a long answer does not push the question off the top.
